# Invariants

Rules a reasonable-looking change could break. Each names the one place that enforces it and the tests that fail if it stops. Test names are in `tests/Sluice.Tests`. The EF package's rules (`SLUICE-EF-`) are in `src/Sluice.EntityFrameworkCore/INVARIANTS.md`. User-facing docs: `docs/`.

## SLUICE-CORE-001 The core references no EF or data-access library

**Rule:** `Sluice` and everything it transitively references contain no `Microsoft.EntityFrameworkCore*`, `Microsoft.Data*`, `System.Data*`, `Npgsql*` or `Dapper` assembly or package.
**Why:** the core is source-agnostic; Dapper, HTTP and file users must not pull in EF.
**Owner:** `src/Sluice/Sluice.csproj` (its package references).
**Proof:** `CoreReferenceTests.The_core_assembly_references_no_EF_or_data_access_library`, `The_core_package_graph_contains_no_EF_or_data_access_package` (the compiler drops unused references from metadata, so only the package graph sees an unused one).

## SLUICE-CORE-002 Invalidation removes entries; it never leaves them as fail-safe fallbacks

**Rule:** the Sluice FusionCache runs with `DisableTagging = false` and `RemoveByTagBehavior.Remove`, both applied after the user's configuration, and `ClearAsync` calls `ClearAsync(allowFailSafe: false)`.
**Why:** under `Expire`, fail-safe and soft timeouts serve a just-invalidated value when the compute fails or is slow; with tagging disabled, every invalidation throws.
**Accepts:** an invalidated entry is gone even when the data source is down, so the caller gets the error, not stale data. FusionCache 2.9.0 can lose an invalidation to a tag check running at the same moment on the same node; SLUICE-CORE-022 publishes every invalidation and clear again to restore it.
**Owner:** `SluiceServiceCollectionExtensions.AddSluice` and `SluiceCache.ClearAsync`.
**Proof:** `FusionCacheConfigurationTests.With_fail_safe_on_a_failing_compute_after_invalidation_throws_instead_of_serving_the_invalidated_value` (its configuration sets `Expire`, so Sluice's override must win), `With_fail_safe_on_a_failing_compute_after_ClearAsync_throws_instead_of_serving_the_cleared_value`, `A_user_who_disables_tagging_still_gets_invalidation`.

## SLUICE-CORE-003 A compute finishes before its caller resumes, and its entry is stamped when it started

**Rule:** every `GetOrSetAsync` passes entry options with infinite `FactorySoftTimeout` and `FactoryHardTimeout`, `AllowTimedOutFactoryBackgroundCompletion = false` and `EagerRefreshThreshold = null`, whatever the user configured, and passes FusionCache no cancellation token: the caller's token goes to the compute and its fused fetches. An already-cancelled token throws before the cache is read.
**Why:** a timed-out factory keeps using the caller's scoped resources after the caller moved on; background completion and eager refresh stamp the entry at completion, so a mid-compute invalidation is ignored; and FusionCache throws on a cancelled token without awaiting its factory.
**Accepts:** a slow data source makes the caller wait. Cancelling doesn't interrupt a wait on another caller's compute or a slow L2 read; `LockTimeout` and the L2 timeouts bound those.
**Owner:** the `SluiceCache` constructor (`_entryOptions`) and `SluiceCache.GetOrSetAsync` (the token).
**Proof:** `FusionCacheConfigurationTests.A_compute_outliving_the_factory_timeout_completes_before_the_caller_resumes` (hard and soft), `A_cancelled_caller_resumes_only_after_its_compute_ends`, `An_already_cancelled_caller_gets_neither_a_hit_nor_a_compute`; through EF, `EntityReadTests.A_factory_timeout_does_not_let_the_caller_reuse_its_context_while_the_compute_s_query_runs`. The background-completion pin can't take effect while both timeouts are infinite, and the eager-refresh pin needs wall-clock time, so neither has a test of its own.

## SLUICE-CORE-004 An entry never outlives the tag data that can invalidate it

**Rule:** at each level the entry's physical lifetime, by FusionCache's own formula, is at most the same figure for `TagsDefaultEntryOptions`: in memory `MemoryCacheDuration ?? Duration`, or `FailSafeMaxDuration` when fail-safe is on and longer, plus the entry's `JitterMaxDuration`; in L2 `DistributedCacheDuration ?? Duration`, or `DistributedCacheFailSafeMaxDuration ?? FailSafeMaxDuration` likewise. The cache defaults are checked when `SluiceCache` is first resolved, and a `Query` with its own `Duration` on every use.
**Why:** once tag data expires the tag reads as never invalidated, so a fresh node serves an invalidated L2 entry, or a memory-only node its own invalidated entry.
**Accepts:** entry lifetimes count from the store and tag data's from the invalidation, so equal lifetimes leave a gap of up to one compute; moot under the defaults.
**Owner:** `EntryLifetime.EnsureWithin`, called from the `SluiceCache` constructor and `SluiceCache.OptionsFor`.
**Proof:** `FusionCacheConfigurationTests.Resolving_SluiceCache_fails_when_an_entry_can_outlive_the_tag_data` (default, distributed and memory durations, both fail-safe lifetimes, memory jitter), `A_query_whose_duration_outlives_the_tag_data_fails_on_first_use`.

## SLUICE-CORE-005 Sluice's keys, tags and clears are isolated from other FusionCaches

**Rule:** the Sluice FusionCache is named `sluice` and uses `WithCacheKeyPrefixByCacheName()`, applied after the user's configuration.
**Why:** a cache name alone doesn't prefix keys, so Sluice's tags and clear would hit any other FusionCache on the same L2.
**Owner:** `SluiceServiceCollectionExtensions.AddSluice`.
**Proof:** `FusionCacheConfigurationTests.Another_FusionCache_on_the_same_L2_is_unaffected_by_Sluice_tags_and_clear` (also when the user turns the prefix off).

## SLUICE-CORE-006 Every tag contains ':', and no clear sentinel can

**Rule:** the tags read and published for a dependency are `n:k`, `n:` and `n:*`; none is a bare source name. Resolving `SluiceCache` throws `InvalidOperationException` when FusionCache's `InternalStrings.ClearRemoveTag` or `ClearExpireTag` has a ':' after a non-blank start, since it could then equal one of them (`a:b` is source `a` key `b`'s tag).
**Why:** FusionCache's clear sentinels (`*`, `!`, or `-rem` and `-exp` after `SetToSafeStrings()`) are ordinary tags, and publishing one clears every other node.
**Accepts:** key text `""` gives the tag `n:`, so invalidating it evicts every reader of the source; that only over-invalidates.
**Owner:** `Dependency.ReadTags` and `Dependency.InvalidationTags`; `Dependency.EnsureNotATag`, called from the `SluiceCache` constructor.
**Proof:** `MultiNodeTests.A_source_named_like_a_clear_sentinel_clears_nothing_on_other_nodes`; `FusionCacheConfigurationTests.Resolving_SluiceCache_fails_when_a_clear_tag_could_be_a_dependency_tag`, `Resolving_SluiceCache_succeeds_with_SetToSafeStrings_defaults` (a clear tag starting with ':' passes).

## SLUICE-CORE-007 A value is cached only with the dependencies its compute recorded

**Rule:** a compute that records no dependency, calls `GetOrSetAsync` itself (a fused fetch included), or uses another compute's `read`, running or already returned (`From`, fused or not, `DoNotCache`, `ActiveCompute.Hold` or `ActiveCompute.BeforeStore`), makes the call throw `InvalidOperationException` and stores nothing. The guard returns from the factory with memory, L2 and backplane writes skipped and rethrows after `GetOrSetAsync` returns; swallowing it in the compute doesn't help. The EF package marks the compute the same way through the hidden public `Sluice.Infrastructure.ActiveCompute` (`Reads`, `InFetch`, `QueryName`, `Violate`), held by the public API files like any other member.
**Why:** a value with no dependencies is never invalidated, a nested hit hides the inner value's dependencies, and another compute's `read` records on that compute what this one read. Throwing from the factory would let fail-safe serve a stale value and hide the bug.
**Accepts:** work started under `ExecutionContext.SuppressFlow` doesn't see the compute, so every guard is off there.
**Owner:** `SluiceCache.GetOrSetAsync`, `SluiceCache.ComputeAsync` and `SluiceCache.FactoryAsync`; for another compute's `read`, `SluiceReads.ThrowIfAnotherCompute`, called from `SluiceReads.Record`, `SluiceReads.Hold`, `SluiceReads.BeforeStore` and `SluiceReads.DoNotCache`.
**Proof:** `ComputeGuardTests.A_compute_that_records_no_reads_throws_and_caches_nothing`, `A_compute_that_records_no_reads_stores_nothing_another_node_can_read`, `A_compute_that_records_no_reads_evicts_nothing_on_another_node`, `Calling_GetOrSetAsync_inside_a_compute_throws`, `Calling_GetOrSetAsync_inside_a_fused_fetch_throws`, `The_zero_reads_guard_throws_and_stores_nothing_even_when_fail_safe_has_an_expired_entry`, `The_nesting_guard_throws_and_stores_nothing_even_when_fail_safe_has_an_expired_entry`, `Using_another_running_compute_s_read_throws_and_caches_nothing` (record-only, fused, `Hold`, `leaves uncached`, and `adds a step before the store`); for a caught EF violation, the EF tests' `TrackedReadTests.A_compute_that_catches_a_violation_caches_nothing_and_its_caller_still_gets_it`.

## SLUICE-CORE-008 No recorded read is lost

**Rule:** every `SluiceReads.From` overload records every dependency passed from any task while the compute runs, and throws once the compute has returned (a fused one before its fetch runs).
**Why:** a read that isn't recorded leaves an entry its data's writes can't evict.
**Owner:** `SluiceReads.From`.
**Proof:** `DependencyTrackingTests.Reads_from_concurrent_tasks_inside_one_compute_are_all_recorded`, `Recording_a_read_after_the_compute_returned_throws`.

## SLUICE-CORE-009 Different query keys never share an entry

**Rule:** without a `format`, `string` keys are used as they are and `IFormattable` keys through `ToString(null, CultureInfo.InvariantCulture)`; any other key type, an interface or abstract key type, and `DateTime`, `DateTimeOffset` and `TimeOnly` are rejected at declaration with a message naming `format`. A `format` is used as given; one that returns null throws. A keyless `Query<TValue>`'s entry key is its name, which no keyed entry key can equal, since those all contain `:` after the name. Query names, keyed or not, can't contain `:` or start with `__fc`, and resolving `SluiceCache` throws `InvalidOperationException` when FusionCache's `InternalStrings.TagCacheKeyPrefix` doesn't start with `__fc`, so no entry key falls under it.
**Why:** a collision serves one key's value to another key's caller. Culture-dependent text splits or merges entries across nodes; the three date types' invariant text drops precision; with an interface key type the runtime type picks the text (`int 1` and `long 1` collide); and FusionCache keeps a tag's marker at its tag prefix plus the tag, among the entries, and treats any key under the prefix as tag data: under the prefix `t:`, query `t` key `x`'s entry is tag `x`'s marker, and is never invalidated.
**Accepts:** a user `IFormattable` type and every `format` are the user's contract. Equal values that print differently (`1.5m`, `1.50m`) only split the cache. Key text is wire format: changing a `format` changes every entry key and tag.
**Owner:** `KeyText.Default` and `KeyText.Of`, plus the name checks in `QueryNames.Claim` and `QueryNames.EnsureTagPrefix`, called from the `SluiceCache` constructor.
**Proof:** `KeyTextTests.*`, `DeclarationTests.Without_a_format_a_key_type_that_is_neither_string_nor_IFormattable_is_rejected`, `Without_a_format_interface_and_abstract_key_types_are_rejected`, `Without_a_format_DateTime_DateTimeOffset_and_TimeOnly_keys_are_rejected`, `A_format_that_returns_null_throws`, `Query_names_containing_a_colon_are_rejected`, `Query_names_starting_with_FusionCache_s_internal_prefix_are_rejected`, `A_keyless_query_name_is_checked_as_a_keyed_one_is`; `FusionCacheConfigurationTests.Resolving_SluiceCache_fails_when_the_tag_key_prefix_is_outside_the_reserved_prefix` (set directly, `SetToSafeStrings` with another special character, blank), `Resolving_SluiceCache_succeeds_with_SetToSafeStrings_defaults`.

## SLUICE-CORE-010 A query or source name is declared with one set of types and one key format

**Rule:** declaring a `Query` name with a second key or value type, or as both a keyed and a keyless query, throws `ArgumentException`, as does declaring a `Source` name with a second key type. Declaring either again with another key format throws `ArgumentException` too. Formats are compared by their method's `(Module.ModuleVersionId, MetadataToken)`: one lambda or method is one format whatever it captures or whichever generic type holds it, two written separately are two even with the same text, and the default format is one per key type. A format compiled from an expression (a `DynamicMethod`) isn't compared; the first format that can be is the one later declarations must match. A repeat with the same types and format is allowed. The hidden public `Sluice.Infrastructure.ModelSource.Create` builds a model's `Source` (the EF package's, named after tables, SLUICE-EF-006), whose name belongs to the model: model sources aren't checked against each other, since a model's names are unique by construction and two models over one table share them on purpose, but declaring an application `Source` with a model's name throws `ArgumentException` naming the EF package's `set.Dependency(key)` and `set.AllDependencies()`, and so does `ModelSource.Create` for a name an application `Source` already has, so the outcome doesn't depend on which comes first. The public API files hold it.
**Why:** two same-named queries share entries, so on a multi-node setup one reads the other's value from L2 as the wrong shape without an error, or `42` and `"42"` share an entry; with two formats one key gets two texts, so its entries split, or two keys share one. Two declarations of one source with different key types or formats give one key different text, so a write through one misses the readers of the other, which keep serving the old value; an application source named like a table has its own format, so an EF save misses its readers and its writes miss EF's.
**Accepts:** copies in other processes aren't caught. One lambda with different captures, and a compiled expression, can still format differently; like any `format`, that's the user's contract (SLUICE-CORE-009). Each registry keeps every distinct name for the life of the process.
**Owner:** `QueryNames.Claim`, called from both `Query` constructors; `SourceNames.Claim`, called from both `Source` constructors, and `SourceNames.ClaimForModel`, called from `ModelSource.Create`; `FormatIdentity`, which both claims use.
**Proof:** `DeclarationTests.Redeclaring_a_query_name_with_a_different_key_or_value_type_throws`, `A_redeclaration_names_types_by_namespace_so_same_named_types_are_told_apart`, `A_keyless_and_a_keyed_query_cannot_share_a_name`, `Redeclaring_a_source_name_with_another_key_type_throws`, `Redeclaring_a_query_or_source_name_with_another_format_throws` (the default and a format, two identical lambdas), `Redeclaring_a_query_or_source_name_with_the_same_types_and_format_is_allowed`, `Redeclaring_a_query_or_source_name_from_one_lambda_with_different_captures_or_generic_holders_is_allowed`, `A_query_or_source_format_from_a_compiled_expression_is_not_compared` (and a later format is still held to the first comparable one), `Model_sources_are_not_checked_against_each_other`, `An_app_source_cannot_share_a_name_with_a_model_source` (the model's first, and the app's first).

## SLUICE-CORE-011 A fused read records its dependencies before its fetch runs

**Rule:** `read.From(dependency, fetch)` and `read.From(dependencies, fetch)` record first, then run the fetch with the compute's token. A fetch that throws leaves the dependencies recorded and propagates unchanged. An empty list throws `ArgumentException` before the fetch runs; the record-only `read.From(dependencies)` accepts one and records nothing.
**Why:** a compute that catches the failure and returns a fallback caches it, and recording only on success would leave the fallback evictable by nothing but the TTL. A fetch that declares nothing would read with the EF origin check off (SLUICE-CORE-013).
**Owner:** `SluiceReads.From<T>(IEnumerable<Dependency>, Func<CancellationToken, Task<T>>)`.
**Proof:** `DependencyTrackingTests.A_fallback_for_a_failed_fused_fetch_is_evicted_by_its_dependency`, `A_failed_fused_fetch_that_escapes_reaches_the_caller_unchanged_and_caches_nothing`, `A_fused_read_returns_the_fetch_result_with_the_compute_token_and_records_the_dependency`, `A_fused_read_of_no_dependencies_throws_before_the_fetch_runs`, `A_record_only_read_of_no_dependencies_counts_as_no_read`.

## SLUICE-CORE-013 A fused fetch is reported as a declared read, to checks of the running compute only

**Rule:** in the flow of a fused fetch, and tasks it starts, `ActiveCompute.InFetch` is true for the running compute's reads. The rest of the compute, a fetch running beside it, and a compute started from its flow are outside it; a record-only `read.From` is no fetch. What each check does there is its own rule: SLUICE-CORE-007, SLUICE-EF-002 and SLUICE-EF-015.
**Why:** the fetch's recorded dependencies cover what it reads, by declaration; it's the route for views, keyless types and raw SQL.
**Accepts:** a fetch's plain query may read rows its declaration doesn't cover, or track; that's the app's declaration. A task the fetch leaves running stays inside it until the compute ends.
**Owner:** `ActiveCompute` (`Fetch` and `InFetch`).
**Proof:** `ComputeGuardTests.Calling_GetOrSetAsync_inside_a_fused_fetch_throws`; the EF tests' `TrackedReadTests.A_query_run_in_a_fused_fetch_is_cached_and_evicted_by_its_declared_dependency`, `A_query_after_a_read_From_that_only_records_is_still_checked`, `While_fused_fetches_run_side_by_side_each_runs_queries_on_any_context_and_the_compute_s_own_flow_does_not`, `A_compute_started_from_a_fused_fetch_that_outlived_its_own_compute_is_checked`, `A_compute_that_catches_a_violation_caches_nothing_and_its_caller_still_gets_it`.

## SLUICE-CORE-014 A compute runs outside the caller's ambient transaction

**Rule:** while a compute runs, `Transaction.Current` is null: `ComputeAsync` suppresses the caller's ambient transaction around it, and the caller has it back once the compute ends.
**Why:** a cached value is served to every caller, so it mustn't see a transaction's uncommitted rows, or an old snapshot. A connection the compute opens would otherwise enlist in the caller's transaction.
**Accepts:** a connection already enlisted before the compute (one the caller opened) stays enlisted; the EF package refuses reads on it (SLUICE-EF-002). A compute that opens its own `TransactionScope` is the app's choice.
**Owner:** `SluiceCache.ComputeAsync`.
**Proof:** `ComputeScopeTests.A_compute_runs_outside_the_caller_s_ambient_transaction_and_the_caller_gets_it_back`; the EF tests' `ReadGuardTests.A_compute_reads_what_is_committed_inside_an_enlisted_transaction_or_a_TransactionScope`.

## SLUICE-CORE-015 What a compute holds lives exactly as long as the compute

**Rule:** `ActiveCompute.Hold` gives a compute one instance of each resource type, made from the application's services on first use, and the compute disposes every one, newest first, once it has returned, before its caller resumes, however it ended (a value, an exception, a cancellation, a violation, no dependencies). A dispose that throws doesn't stop the rest, and never throws out of the FusionCache factory: it's recorded as a violation, so nothing is stored even with fail-safe on and an expired entry. The caller gets a guard violation first; else the compute's exception and the dispose's together in an `AggregateException`; else the dispose's exception (an `AggregateException` for several). Holding something after the compute returned throws. `ActiveCompute.Held` returns the instance a compute holds of a type, or null, and makes nothing. Both are hidden public members of `Sluice.Infrastructure.ActiveCompute`, held by the public API files.
**Why:** the EF package's `read.Db` context must be the compute's own: created inside it, recognisable as its own (through `ActiveCompute.Held`, which a check can ask without opening anything), and gone with it, so nothing it read outlives the compute. A throw from the factory would replace the compute's exception or violation, skip the no-dependencies guard, and let fail-safe serve the expired value.
**Accepts:** a task the compute leaves running may find its resource disposed. A resource that disposes others by its own rules keeps those rules: the EF package's DI scope stops at the first of its services whose dispose throws, so the rest of that scope's aren't disposed (SLUICE-EF-001). A dispose that throws after a guard violation is dropped: the caller gets the violation. A cancelled compute whose dispose throws reaches the caller as an `AggregateException`, not an `OperationCanceledException`.
**Owner:** `SluiceReads.Hold`, `SluiceReads.Held` and `SluiceReads.ReleaseAsync`, called from `SluiceCache.ComputeAsync`.
**Proof:** `ComputeScopeTests.What_a_compute_holds_is_one_instance_per_type_and_is_disposed_when_it_ends`, `What_a_compute_holds_is_disposed_newest_first`, `What_a_compute_holds_is_disposed_however_the_compute_ends` (throws, is cancelled, records a violation, records no dependencies), `When_one_held_resource_s_dispose_throws_the_rest_are_still_disposed_and_its_exception_reaches_the_caller`, `When_several_held_resources_dispose_throws_all_are_disposed_and_the_caller_gets_every_exception`, `When_the_compute_throws_and_a_dispose_throws_the_caller_gets_both_and_nothing_is_cached`, `When_the_compute_records_a_violation_and_a_dispose_throws_the_caller_gets_the_violation`, `A_dispose_that_throws_stores_nothing_even_when_fail_safe_has_an_expired_entry`, `Held_returns_what_the_compute_holds_and_makes_nothing`; the EF tests' `ComputeContextTests.A_compute_gets_one_context_that_does_not_track_and_is_disposed_when_it_ends`.

## SLUICE-CORE-017 A value whose compute called `read.DoNotCache()` is never stored

**Rule:** once a compute calls `read.DoNotCache()` on its own `read`, the factory returns its value with memory, L2 and backplane writes skipped, as for a violation, so the caller gets the value and nothing is stored; such a compute may record no dependencies without the "recorded no dependencies" violation. A violation still wins: the call throws and stores nothing. A call after the compute returned throws; a call on another compute's `read` is a violation of the compute making the call (SLUICE-CORE-007).
**Why:** a key from public input (a slug from a URL) would otherwise cache every miss, so any caller could fill memory; and Sluice has no remove-by-key to undo a store.
**Accepts:** FusionCache hands a waiting caller only what the running compute stored, so callers waiting on the same key each run their own compute, one at a time, once it ends.
**Owner:** `SluiceReads.DoNotCache` and `SluiceReads.Close`, read by `SluiceCache.FactoryAsync`.
**Proof:** `CachingTests.An_uncached_value_goes_to_the_caller_and_the_next_call_computes_again` (no dependencies recorded), `A_compute_can_leave_its_value_uncached_from_inside_a_fused_fetch`, `A_caller_waiting_on_an_uncached_compute_gets_a_value_from_its_own_compute`, `A_violation_still_throws_and_caches_nothing_when_the_compute_left_its_value_uncached`, `Leaving_a_value_uncached_after_the_compute_returned_throws`; `ComputeGuardTests.An_uncached_value_is_stored_nowhere_another_node_can_read` (no L2 write), `An_uncached_value_evicts_nothing_on_another_node` (no backplane message), `Using_another_running_compute_s_read_throws_and_caches_nothing` (`leaves uncached`).

## SLUICE-CORE-018 Tag markers are never evicted by a memory size limit

**Rule:** `AddSluice` sets `TagsDefaultEntryOptions.Priority = NeverRemove` and `TagsDefaultEntryOptions.Size = 0`, after the user's configuration. FusionCache writes every tag and clear marker with these options. A query's `Size` is its value entry's size; `null` keeps `DefaultEntryOptions.Size`.
**Why:** under a `SizeLimit`, a marker that compaction removes, or that the memory cache refuses for want of room, reads as never invalidated, so the invalidated value is served again.
**Accepts:** markers aren't counted against the limit, so they can grow past it: one small entry per tag a node has seen, until its tag-data lifetime ends. With a limit set, an entry with no size makes the memory cache throw, so the app sets `DefaultEntryOptions.Size` or each query's `Size`.
**Owner:** `SluiceServiceCollectionExtensions.AddSluice` (the markers); `SluiceCache.OptionsFor` (a query's size).
**Proof:** `FusionCacheConfigurationTests.Under_a_size_limit_an_invalidated_value_never_comes_back` (compacted, and no room; the app's options ask for markers that can be evicted and take room), `A_query_s_size_is_its_entry_s_size_in_a_memory_cache_with_a_size_limit`.

## SLUICE-CORE-019 Inside a flow with uncommitted writes, a read computes fresh, stores nothing, and throws if it depends on them

**Rule:** before it touches FusionCache, `GetOrSetAsync` gathers what this cache's probes in the flow's `SluiceFlow` box report as pending, plus what the cache's ambient lookup reports for the caller's `Transaction.Current`, read before the compute suppresses it (SLUICE-CORE-014). If anything is pending, the call doesn't read, store or take FusionCache's stampede lock: the compute runs as on a miss, with every guard, its held resources, its `BeforeStore` steps and `DoNotCache`, and its value goes to the caller uncached, unless a tag it recorded is among the pending dependencies' invalidation tags, which makes the call throw `InvalidOperationException` naming the query and those dependencies. An empty report takes the normal path. A probe belongs to one cache; another cache's is never called. `SluiceFlow.Begin` inside a flow that has a box returns a handle that does nothing, and disposing the outermost handle removes the box. Packages reach the box and the lookup through the hidden public `Sluice.Infrastructure.FlowWrites`: `AddProbe` keeps nothing and returns false without a box, and the box keeps one probe per cache and key (a value compared with `Equals`, such as a transaction's id), so a probe for a key it already holds for that cache isn't kept; `OnAmbient` holds one lookup per cache, a later call replacing it. Both are held by the public API files.
**Why:** a compute runs outside the caller's transaction (SLUICE-CORE-014), so a value cached or computed while that transaction holds uncommitted writes it read lacks them, which breaks read-your-own-writes. A hit can't be checked, since values are stored unwrapped and FusionCache doesn't return a hit's tags, so every read is fresh while writes are pending. Staying out of the stampede lock keeps a caller without pending writes from waiting on one with them, or inheriting its violation. The overlap test is the invalidation rule (SLUICE-CORE-006's tags), so a read throws exactly when committing the writes would evict its entry.
**Accepts:** while writes are pending, every read in the flow hits the data source. A call costs one `AsyncLocal` read with no box, plus a `Transaction.Current` read once a package has registered an ambient lookup; with a box, one call per probe. The box keeps its probes until its outermost handle is disposed, and tasks the flow left running still see it; one probe per key keeps that to one per transaction, however often the flow writes in it. What the probes report is the package's: a transaction it doesn't see isn't checked (the EF package's rule is SLUICE-EF-025).
**Owner:** `SluiceCache.GetOrSetAsync` (`PendingWrites` and `BypassAsync`), and `SluiceFlow` (`Begin`, its box and `Pending`).
**Proof:** `ComputeGuardTests.A_read_of_the_flow_s_uncommitted_writes_throws_caches_nothing_and_after_the_flow_caches_as_usual`, `With_unrelated_uncommitted_writes_a_read_computes_fresh_and_stores_nothing` (a value cached earlier isn't returned, and stays), `With_uncommitted_writes_a_read_keeps_its_guards_and_steps` (no dependencies, uncached, a step's read), `A_probe_with_nothing_pending_leaves_reads_cached_as_usual`, `Uncommitted_writes_overlap_a_read_as_an_invalidation_would` (a key read and a whole-source write, and the reverse), `Another_cache_s_uncommitted_writes_are_ignored`, `A_read_inside_an_ambient_transaction_with_uncommitted_writes_it_depends_on_throws`, `Without_a_flow_box_a_probe_is_not_kept`, `A_probe_with_a_key_the_box_already_holds_is_not_kept` (keys compared by value; another key, or another cache's same key, is kept), `A_nested_flow_shares_the_outer_box_and_only_the_outermost_handle_removes_it`; `RaceTests.Callers_with_and_without_uncommitted_writes_on_one_key_neither_wait_on_nor_fail_each_other` (whichever starts first).

## SLUICE-CORE-020 A compute's before-store steps run inside it, before anything is stored

**Rule:** `ActiveCompute.BeforeStore` adds a step to the compute; adding one after the compute returned throws `InvalidOperationException`, and adding one to another compute's `read` is a violation (SLUICE-CORE-007). Once the compute returns a value, the steps run in the order added, a step added by a step included, inside the same `try` as the compute and the same ambient-suppressing scope, on its flow and with its token: `ActiveCompute.Reads` is still the compute's, `read.From` still records, and nothing it holds is disposed yet. Then the compute is closed and its tags taken. Steps don't run when the compute threw, and don't run, or stop, once it has a violation, or once it has called `DoNotCache` unless the call took SLUICE-CORE-019's bypass, where what they record is checked against the pending writes. A step that throws is the compute's exception: the rest don't run, nothing is stored, and the caller gets it (with any dispose failure, as SLUICE-CORE-015 says). It is a hidden public member of `Sluice.Infrastructure.ActiveCompute`, held by the public API files.
**Why:** the EF package's read by a unique column records the key of each row it found in a step (SLUICE-EF-023). The step must run as the compute, so its query passes the read checks on the compute's own context, and before the tags are taken, so what it records is stored with the value. A step that failed without failing the compute would cache the value without them.
**Accepts:** a step runs after the compute's own reads, so what it looks up may have changed in between; a write that changed it publishes after the compute started, which evicts the entry (SLUICE-CORE-003). A step added from a task the compute didn't await, once the steps have run but before the compute is closed, also throws (`SluiceReads` marks its steps run under the same lock as their last count), but no test can reach that window deterministically, so it is enforced and not proved.
**Owner:** `SluiceReads.BeforeStore` and `SluiceReads.RunBeforeStoreAsync`, called from `SluiceCache.ComputeAsync`.
**Proof:** `ComputeScopeTests.Steps_run_in_order_after_the_compute_returns_and_before_its_value_is_stored`, `A_step_added_by_a_step_runs_too`, `A_step_that_throws_fails_the_call_and_caches_nothing`, `Steps_do_not_run_when_nothing_will_be_stored` (throws, records a violation, leaves uncached), `Adding_a_step_after_the_compute_returned_throws`, `A_step_runs_outside_the_caller_s_ambient_transaction`; `ComputeGuardTests.Using_another_running_compute_s_read_throws_and_caches_nothing` (`adds a step before the store`).

## SLUICE-CORE-021 A value is stored only after its cache's store checks pass

**Rule:** `Sluice.Infrastructure.StoreChecks.Add` registers a check in the service collection, and the `SluiceCache` built from it takes every registered check when it's constructed, before its first compute; one equal to a check already registered isn't registered again. Once a compute and its before-store steps have returned (SLUICE-CORE-020), inside the same `try`, on the compute's flow and before what it holds is disposed, the checks run in the order added on a value that will be stored: not null, from a compute that recorded dependencies, has no violation, didn't call `DoNotCache` and didn't take SLUICE-CORE-019's bypass. The first check that returns an exception makes it the compute's violation, so nothing is stored and the caller gets it (SLUICE-CORE-007); the rest don't run. A check that throws is the compute's exception. A hit isn't checked. It is a hidden public member, held by the public API files.
**Why:** the EF package refuses a value holding a lazy loader or a `DbContext` (SLUICE-EF-027), which would load rows later, outside the compute and with no dependency recorded, or keep the compute's context alive for every caller. The core has no EF reference (SLUICE-CORE-001), so the package registers the check with its services (`AddSluiceEntityFrameworkCore`); a check added later, when a context is first configured, would miss the computes that ran before it, often the first. A value that isn't stored reaches only its own caller, so checking it would only cost.
**Accepts:** every stored value costs a call per check.
**Owner:** `SluiceCache.ComputeAsync` (the checks) and `SluiceReads.WillStore`.
**Proof:** `ComputeScopeTests.A_store_check_that_refuses_a_value_fails_the_call_and_caches_nothing` (on the compute's flow with what it holds still open, added once, a hit and a null value not checked), `Store_checks_do_not_run_when_nothing_will_be_stored` (throws, records a violation, records no dependencies, leaves uncached, runs while the flow has uncommitted writes).

## SLUICE-CORE-022 Every invalidation and clear is published again 5 s later

**Rule:** once `InvalidateAsync`, `Invalidate` or `ClearAsync` has published, it publishes the same tags, or the clear, again `SluiceCache.RepublishDelay` (5 s) later, timed by the `TimeProvider` registered in DI, or `TimeProvider.System`. An invalidation of no dependencies publishes nothing, and one whose first publish throws isn't published again. Disposing `SluiceCache`, asynchronously or not, publishes every re-publish still waiting at once and waits for them all, and throws nothing. A re-publish runs with the caller's execution context suppressed, so it holds none of the caller's async state (its ambient transaction, `AsyncLocal`s, trace). Every re-publish failure ends in `PublishAgainAsync`: it reaches no caller and not the dispose, and leaves no faulted task unobserved. FusionCache logs failed memory, distributed cache and backplane writes; one that finds FusionCache disposed is shutdown's.
**Why:** FusionCache 2.9.0 writes a tag's marker without the lock its tag check holds, and the check writes what it read unconditionally, so an invalidation landing between the check's re-read and its write is overwritten, and the invalidated entries are served on that node until the tag is invalidated again (FusionCache#659). It opens on a tag's first check and each time its marker's memory entry expires, and a backplane invalidation from another node takes the same path. The losing check leaves its marker in memory, so the second publish sticks unless another check's distributed cache read outlasts the delay, 5 s being StackExchange.Redis's default timeout. Rejected: a per-tag lock in Sluice (the check runs inside FusionCache, and backplane writes bypass Sluice), and a memory cache wrapper guarding markers (it relies on FusionCache internals and turns off its raw clear).
**Accepts:** a lost invalidation is served on one node for up to 5 s, and stays lost only if a tag check's distributed cache read there outlasts 5 s; a marker whose memory lifetime is under 5 s heals from L2 at its next check. Values cached in those 5 s are evicted again, so a hot entry is computed once more per invalidation. Every invalidation writes its tags, and every clear its marker, to L2 and the backplane twice, and each holds a timer and its tag list for 5 s. A process that stops without disposing its service provider drops what is still waiting.
**Owner:** `SluiceCache.PublishAgainLater` (and `SluiceCache.PublishAgainAsync`, which it starts), called from `SluiceCache.InvalidateAsync`, `SluiceCache.Invalidate` and `SluiceCache.ClearAsync`, and `SluiceCache.DisposeAsync`.
**Proof:** `RaceTests.An_invalidation_a_concurrent_tag_check_overwrote_is_restored_when_it_is_published_again` (its precondition reproduces FusionCache's race deterministically, so it fails once FusionCache fixes it and the workaround can go), `Each_invalidation_is_published_again_after_the_delay_and_not_before` (`InvalidateAsync` of one and of many, `Invalidate`), `Disposing_the_cache_publishes_pending_re_invalidations_at_once_and_throws_nothing` (asynchronously and synchronously), `ClearAsync_is_published_again_after_the_delay`, `A_re_publish_holds_none_of_the_caller_s_async_state`, `A_failing_re_publish_reaches_no_one` (FusionCache disposed first, a memory write that throws); `MultiNodeTests.A_re_invalidation_reaches_other_nodes`.
