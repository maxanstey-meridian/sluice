# Invariants

Rules a reasonable-looking change could break. Each names the one place that enforces it and the tests that fail if it stops. Test names are in `tests/Sluice.EntityFrameworkCore.Tests`. The core's rules (`SLUICE-CORE-`) are in `src/Sluice/INVARIANTS.md`. User-facing docs: `docs/guides/ef-core.md`, `strict-reads.md` and `transactions.md`.

## SLUICE-EF-001 A compute's EF reads run on its own context, which tracks nothing by default and loads only what it asks for

**Rule:** `read.Db<TContext>()` returns one context per compute, made by the registered `IDbContextFactory<TContext>` with `QueryTrackingBehavior.NoTracking`, and disposed when the compute ends (SLUICE-CORE-015). `read.Entity` and `read.Children` return `AsNoTracking()` queries that call `IgnoreAutoIncludes()`; owned navigations still load, since EF ignores `IgnoreAutoIncludes()` for ownership.
**Why:** a context from outside the compute can hand back tracked instances with unsaved edits, or rows it loaded before a write evicted the value, and the cache would serve them to everyone. A fresh context holds only what the compute itself read.
**Accepts:** cached entities are detached; to edit one, load it again. A query with `AsTracking()` tracks into the compute's context, which nobody else sees. EF applies a helper's `IgnoreAutoIncludes()` to the whole query, so a plain query joined or combined with a helper's loads no auto-included navigations either (and the analysis, SLUICE-EF-016, reads it the same way).
**Owner:** `SluiceReadsExtensions.Db`, and `TrackedReads.Query`, which every helper's query starts from.
**Proof:** `ComputeContextTests.A_compute_gets_one_context_that_does_not_track_and_is_disposed_when_it_ends`, `EntityReadTests.Reads_do_not_track_so_an_unsaved_edit_on_the_callers_context_is_not_cached`, `TrackedReadTests.A_read_helper_does_not_load_auto_included_navigations`.

## SLUICE-EF-002 EF reads inside a compute refuse to run inside a transaction

**Rule:** while a compute runs, a read on a `UseSluice` context throws `InvalidOperationException` when it executes inside the context's EF transaction, an enlisted one or an ambient one, read from the context when the command runs, as EF's batch executor reads it (so `Enlist=false` doesn't count). The compute's own context never enlists in the caller's transaction (SLUICE-CORE-014), so this catches a transaction the compute opens itself, and reads in a fused fetch on a context that's in one.
**Why:** a compute inside a transaction caches rows others can't see yet, which may roll back, or an old snapshot, and serves them to everyone.
**Accepts:** generic-path computes aren't checked. A raw `DbTransaction` on the context's connection isn't seen.
**Owner:** `TrackedReads.Read`, through `ContextTransaction.Of`, which the write side (SLUICE-EF-007) uses too.
**Proof:** `TrackedReadTests.A_query_that_opens_a_transaction_on_the_compute_s_context_throws`, `A_compute_that_catches_a_violation_caches_nothing_and_its_caller_still_gets_it` (the fused-fetch case); `ReadGuardTests.A_compute_reads_what_is_committed_while_the_caller_s_EF_transaction_is_open`, `A_compute_reads_what_is_committed_inside_an_enlisted_transaction_or_a_TransactionScope`.

## SLUICE-EF-003 Types not mapped to a table are refused

**Rule:** the read helpers, `set.Dependency(key)` and `set.AllDependencies()` throw `NotSupportedException` for keyless types and types mapped with `ToView`, `ToFunction`, `ToSqlQuery` or to no table; inside a compute, a query that reads one throws `InvalidOperationException` (SLUICE-EF-015). A type is mapped when it (unless it's abstract, like a TPC root with no table) and every concrete type under it is stored in a table, since a query of the type returns those too: a table-mapped TPC root with a view-mapped type under it is refused. The check is on each type a query reads, not its root: a query on a table-mapped type whose TPC root also has a view under it is tracked, and records the root's whole-type dependency.
**Why:** no tracked write publishes for those types, so a cached read of one would only expire.
**Accepts:** such data is cached through a fused fetch with a declared `Source`, invalidated by hand.
**Owner:** `ModelSources.EnsureTable`, and `ModelSources.Unmapped` for the query analysis; `TrackedReads.Dependencies` takes the root's source without the check, which the analysis has already made.
**Proof:** `ReadGuardTests.Helper_reads_and_dependencies_of_types_not_mapped_to_a_table_throw`, `A_type_stored_in_a_table_with_a_derived_type_mapped_to_a_view_is_refused`, `TrackedReadTests.A_command_Sluice_cannot_track_throws_inside_a_compute_and_runs_outside_one`; for the TPC root, `EntityReadTests.A_derived_type_shares_its_root_type_dependencies`, `WriteDerivationTests.Editing_a_derived_row_evicts_readers_of_its_root_type_with_TPH_TPT_or_TPC` and `TrackedReadTests.A_query_on_a_table_mapped_type_whose_TPC_root_has_a_view_is_cached_and_evicted_by_a_write_to_it`.

## SLUICE-EF-004 EF keys are typed by the model

**Rule:** a key passed to `read.Entity` or `set.Dependency` has exactly the CLR type of the single-column primary key, and one passed to `read.Children` that of the FK property, nullability ignored; otherwise `ArgumentException` names the expected type. Composite primary keys throw `NotSupportedException` for single-row reads and dependencies.
**Why:** a key of another type (`1L` for an `int` key, a raw value for a typed id) formats to its own text, so a read and a write of one row could record different dependencies.
**Owner:** `ModelSources.EnsureKeyType` and `ModelSources.KeyProperty`.
**Proof:** `ReadGuardTests.A_key_of_the_wrong_type_throws_naming_the_expected_type`, `A_nullable_foreign_key_takes_a_key_of_its_underlying_type`, `Reading_or_invalidating_one_row_by_composite_key_throws_but_the_whole_set_works`.

## SLUICE-EF-005 EF key text is the folded column value

**Rule:** a model-derived key's text is its provider value, through the property's value converter, then folded: `decimal` scale normalised, strings right-trimmed and upper-cased invariantly, `DateTime` (local to UTC) and `DateTimeOffset` as ticks truncated to microseconds, `byte[]` as hex, other `IFormattable` values invariant.
**Why:** values the database treats as equal (`1m` and `1.00m` in `numeric`, `abc` and `ABC` in `citext`) must give one dependency, or a write keyed one way misses a reader keyed the other.
**Accepts:** folding can merge values the database tells apart, which only over-invalidates. Accent- and culture-sensitive collations aren't folded.
**Owner:** `ModelSources.Build` (with `ModelSources.ToProvider`) and `KeyFolding.Fold`.
**Proof:** `FoldedKeyTests.A_numeric_key_read_as_1_is_evicted_by_the_same_value_written_as_1_00`, `A_citext_key_read_in_one_case_is_evicted_by_the_same_key_in_another`, `A_strongly_typed_key_folds_the_value_its_converter_stores`, `KeyFoldingTests.*`.

## SLUICE-EF-006 Model-derived sources are named by EF's root entity type

**Rule:** an entity type's source is named `IEntityType.GetRootType().Name`, and a foreign key's `<root type name>[<FK property names, comma-joined>]`, built once per model through the core's public `Source<object>(name, format)` and kept as model annotations. Writes use the same sources.
**Why:** reads and writes of derived types (TPH, TPT, TPC), and every `Children` form, must meet on one source. The names are wire format.
**Owner:** `ModelSources.WrittenEntity` (which `ModelSources.Entity` checks and returns) and `ModelSources.ForeignKey`.
**Proof:** `EntityReadTests.A_derived_type_shares_its_root_type_dependencies`, `ChildrenReadTests.Each_Children_form_depends_on_the_foreign_key_value_it_reads`, `WriteDerivationTests.Editing_a_derived_row_evicts_readers_of_its_root_type_with_TPH_TPT_or_TPC`.

## SLUICE-EF-007 A tracked write is invalidated after it commits, before the call that committed it returns

**Rule:** a save's invalidations publish once the transaction it ran in has ended, before the call that ended it returns: `SaveChanges` without a transaction; `Commit` or `Rollback` of an EF transaction, on whichever context calls it (disposed without either, nothing); completion of an enlisted or ambient transaction, whatever the outcome. The transaction is read when the save completes, as EF's batch executor reads it. Every context on one `SluiceCache` shares the interceptor, so a commit publishes other contexts' saves in its transaction.
**Why:** publishing before the commit lets a reader re-cache the old row in between, and nothing evicts it until it expires.
**Accepts:** a promoted or distributed transaction can complete after `TransactionScope.Dispose` returns. A scope without `TransactionScopeAsyncFlowOption.Enabled` can leave an async save seeing no transaction, so it publishes at once. Ambient saves publish one batch each, on the completing thread; an EF transaction publishes one de-duplicated batch. A leftover save (SLUICE-EF-008) publishes early, then again from its live transaction. A `DbTransaction` committed outside EF, a commit on a context without `UseSluice`, and a crash between commit and publish aren't covered.
**Owner:** `SluiceInterceptor`.
**Proof:** `PublishTimingTests.Without_a_transaction_a_save_is_evicted_only_once_its_write_has_run`, `Inside_an_EF_transaction_a_save_is_evicted_only_once_the_transaction_commits`, `A_transaction_disposed_without_commit_evicts_nothing_even_when_its_connection_commits_later`, `A_save_on_a_context_sharing_another_context_s_transaction_is_evicted_when_it_commits`, `A_transaction_the_execution_strategy_retries_is_evicted_when_its_retry_commits`, `A_save_whose_transaction_an_interceptor_commits_before_Sluice_sees_the_save_complete_is_evicted`; `AmbientTransactionTests.Inside_a_TransactionScope_a_save_is_evicted_only_once_the_scope_completes_whatever_its_outcome`, `Inside_an_enlisted_transaction_a_save_is_evicted_only_once_it_completes_whatever_its_outcome`, `Contexts_saving_inside_one_TransactionScope_are_all_evicted_when_it_completes`, `With_Enlist_false_a_save_inside_a_TransactionScope_is_evicted_at_once_and_outlives_the_scope`; `RandomWorkloadTests.Once_concurrent_random_reads_and_writes_settle_every_cached_read_matches_a_fresh_one`.

## SLUICE-EF-008 Every save outcome that might have committed something publishes

**Rule:** a failed, cancelled or conflicting save (`SaveChangesFailed`, `SaveChangesCanceled`, `ThrowingConcurrencyException`) publishes what it captured by SLUICE-EF-007's timing, and a save that goes on past a suppressed conflict publishes again. A rollback, a failed commit and a failed savepoint release publish what the transaction's saves wrote; the later commit or rollback still publishes everything. A capture still held when the context saves again (a leftover: an outer save of a nested save, or one ended without an event) publishes at once, and again from the transaction it began in if that's still live, never from the next save's transaction.
**Why:** earlier batches can commit before a later one fails, and a failed commit's outcome is unknown. EF ends an inner save before its outer one, so an outer save not published by then never would be. Over-invalidating is safe; a dropped invalidation isn't.
**Accepts:** failed saves over-invalidate rows that never committed; a savepoint failure and a leftover publish more than once.
**Owner:** `SluiceInterceptor`.
**Proof:** `PublishTimingTests.A_save_that_fails_after_an_earlier_batch_committed_evicts_that_batch`, `A_concurrency_conflict_after_an_earlier_batch_committed_evicts_that_batch`, `A_save_that_goes_on_past_a_suppressed_concurrency_conflict_evicts_what_it_commits_after_it`, `A_save_cancelled_after_an_earlier_batch_committed_evicts_that_batch` (async only: a sync save takes no token), `A_rolled_back_transaction_still_evicts_what_its_saves_wrote`, `A_commit_that_fails_still_evicts_what_its_saves_wrote`, `A_savepoint_that_fails_to_release_does_not_stop_the_commit_evicting_every_save_in_the_transaction`, `A_save_an_interceptor_makes_from_inside_another_save_evicts_what_both_saves_wrote`, `A_committed_save_is_evicted_though_an_interceptor_then_saves_again_in_a_transaction_it_never_commits`, `Inside_an_EF_transaction_a_save_an_interceptor_saves_again_after_is_evicted_once_more_when_the_transaction_commits`; `AmbientTransactionTests.A_save_left_behind_by_a_conflict_in_a_disposed_TransactionScope_is_evicted_by_the_next_save_without_failing_it`.

## SLUICE-EF-009 Publishing after a commit never throws and can't be cancelled

**Rule:** every publish catches any exception and logs it at `Error`, event id 1, through `ILogger<SluiceInterceptor>` from the services passed to `UseSluice` (which throws without logging); the save, bulk write, commit or completion returns normally. Publishing uses the core's token-less `InvalidateAsync` and `Invalidate`, ignoring EF's token.
**Why:** a throw after the commit makes callers retry a committed write; a request cancelled just after its commit must still invalidate.
**Accepts:** a failed publish leaves stale values until they expire, visible only in the log. An L2 that fails a tag write doesn't fail the publish: FusionCache writes the tag again once the L2 is back (auto-recovery). A slow L2 delays `SaveChanges` until the Redis client times out, since FusionCache puts no timeout on writes; the client's timeout and FusionCache's circuit breakers bound it. Inside a transaction, deriving the dependencies happens at `SavedChanges` (a bulk write's when its command ends), before the commit, where a failure still throws. A leftover's are derived inside its publish, so a failure to derive them is logged, not thrown into the unrelated save that found it.
**Owner:** `SluiceInterceptor.Publish` and `SluiceInterceptor.PublishAsync`.
**Proof:** `PublishTimingTests.A_failure_to_invalidate_after_commit_is_logged_and_the_write_returns_normally`, `Cancelling_the_request_just_after_its_save_committed_still_evicts`, `Cancelling_the_request_just_after_its_transaction_committed_still_evicts`; for an L2 that fails writes, the core tests' `MultiNodeTests.A_distributed_cache_that_fails_writes_does_not_make_InvalidateAsync_throw_and_the_tag_is_written_once_it_recovers`.

## SLUICE-EF-010 Sync EF calls publish synchronously

**Rule:** sync `SaveChanges`, `ExecuteUpdate`, `ExecuteDelete`, `Commit`, `Rollback`, their failure paths, and an enlisted or ambient transaction's `TransactionCompleted` event publish through `SluiceCache.Invalidate`, never by blocking on the async path.
**Why:** sync-over-async can deadlock under a synchronization context and ties up a thread-pool thread per call.
**Owner:** `SluiceInterceptor.Publish`.
**Proof:** `PublishTimingTests.Sync_SaveChanges_Commit_Rollback_and_their_failures_evict_without_going_through_async_code`, `BulkWriteTests.Sync_ExecuteUpdate_and_ExecuteDelete_evict_without_going_through_async_code`, `AmbientTransactionTests.A_completing_TransactionScope_evicts_without_going_through_async_code`. Their L2 throws on any async call, which FusionCache logs as a warning; the first test shows an async call does log one.

## SLUICE-EF-011 Capturing a save doesn't change what EF saves

**Rule:** a save on a context with `UseSluice` writes exactly what it would without it: an edit EF wouldn't detect (with `AutoDetectChangesEnabled` off) stays unsaved and uninvalidated, and a cascade the app's timings leave to the database or set to `Never` isn't applied.
**Why:** an unconditional `DetectChanges()` saves edits the app chose not to detect, and EF's public `CascadeChanges()` forces every cascade.
**Accepts:** with one timing `OnSaveChanges` and the other `Never`, point readers of rows EF cascades during the save through `ClientCascade` or `ClientSetNull` aren't evicted (`Children` readers are; `Cascade` and `SetNull` are covered by SLUICE-EF-012). The tracker may be scanned up to three times per save.
**Owner:** `CapturedSave.Capture`.
**Proof:** `WriteDerivationTests.With_change_detection_off_an_undetected_edit_is_neither_saved_nor_invalidated`, `With_orphan_deletion_off_Sluice_does_not_make_EF_delete_an_orphan`, `With_cascades_on_save_deleting_a_principal_evicts_readers_of_its_tracked_dependents`.

## SLUICE-EF-012 A save invalidates real keys and its foreign keys before and after

**Rule:** each changed row (join and composite-key rows included) invalidates its key and each foreign key's value before and after the save, skipping nulls; originals are read in `SavingChanges`, keys and current values after the save. A foreign key the tracker can't vouch for invalidates every `Children` reader of it: marked modified with original equal to current (`Update()` of an unloaded object), or an original that's null in a required key or equal to EF's sentinel for the property (the CLR default, such as 0, unless `HasSentinel` says otherwise). A primary key temporary again after a failed save invalidates its type's `All`, and a foreign key still temporary its source's `All`. A deleted row also invalidates every foreign key that references it, by that key's principal value, and whatever the model lets the database do to rows of other types: for each non-ownership foreign key to the row's type (or a base or derived type) whose `DeleteBehavior` is `Cascade` or `SetNull`, the dependent type's `All` (an owned dependent counts as its owner) and every other foreign key of the dependent, whole; for `Cascade`, then the same for the dependent's own cascading foreign keys, each whole, transitively, visiting each type once. Table-per-type links between a derived type's table and its base's are the same row, not a cascade. A row deleted through a base type also invalidates, whole, every foreign key that references only a derived type, since it may be one. `Restrict`, `NoAction`, `ClientCascade` and `ClientSetNull` add nothing. The closure is built once per type. A write to a type the helpers refuse still publishes without failing the save.
**Why:** EF overwrites originals when it accepts the save, and an unloaded object has none; generated keys are temporary until the save runs, and again after a failure; database `CASCADE` and `SET NULL` delete or change rows the tracker never loaded, whose keys only a query before the delete could tell (rejected: an extra round trip per delete, and it races other writers).
**Accepts:** `Update()`, stubs and a real default-valued foreign key (a seeded 0) over-invalidate `Children` readers. A stub whose key holds any other value looks loaded and invalidates the parent it names, so when that isn't the stored one (a nullable key left null, a value from a constructor), the real old parent is missed. A delete over-invalidates by whole type: deleting one customer evicts every cached read of orders (and order lines, and every other type it cascades into). Cascades the model doesn't know about (triggers, a database-first schema that drifted from the model) aren't covered. Changes from an interceptor that runs after Sluice's `SavingChanges` aren't captured. Two entity types splitting one table and sharing a non-key column: saving one changes the column, but only its own root's source is invalidated, so the other's `Entity` and `All` readers keep the old value.
**Owner:** `CapturedSave`, with the cascade closure in `ModelSources.Cascades`.
**Proof:** `WriteDerivationTests.Re_parenting_a_child_evicts_Children_readers_of_both_parents`, `Re_parenting_through_a_navigation_or_a_shadow_foreign_key_evicts_every_Children_form_of_both_parents`, `Removing_a_row_that_was_never_loaded_evicts_Children_readers_of_its_parent`, `Removing_a_row_that_was_never_loaded_with_its_required_foreign_key_set_to_null_evicts_Children_readers_of_its_parent`, `Updating_a_row_from_an_object_that_was_never_loaded_evicts_Children_readers_of_its_old_parent`, `A_partial_update_of_a_row_that_was_never_loaded_evicts_Children_readers_of_its_parent`, `Inserting_rows_evicts_earlier_not_found_reads_of_their_generated_keys`, `Deleting_a_principal_evicts_Children_readers_of_rows_the_database_deletes_or_sets_to_null`, `Adding_editing_or_deleting_a_child_evicts_Children_readers_of_its_parent_only`, `Setting_a_nullable_foreign_key_to_or_from_null_evicts_Children_readers_of_its_principal`, `A_foreign_key_to_an_alternate_key_evicts_Children_readers_of_that_key`, `Linking_or_unlinking_many_to_many_rows_evicts_Children_readers_of_the_join_rows_on_both_sides`, `Writing_a_composite_key_row_evicts_its_Children_and_All_readers`, `A_save_that_also_writes_a_type_reads_refuse_still_evicts_the_rest`, `Deleting_a_principal_evicts_every_reader_of_the_rows_the_database_cascades_into_at_any_depth`, `Deleting_a_principal_evicts_every_reader_of_the_rows_the_database_sets_to_null`, `Deleting_a_principal_evicts_nothing_more_for_dependents_the_database_leaves_alone`, `A_cascade_from_a_type_to_itself_evicts_readers_at_every_depth_and_ends`, `Deleting_a_row_evicts_no_reader_of_another_row_of_its_type`, `Deleting_a_derived_row_through_a_base_type_stub_evicts_lists_through_foreign_keys_into_the_derived_type`; `PublishTimingTests.A_row_inserted_by_a_committed_batch_of_a_failed_save_evicts_readers_of_its_type`, `A_row_inserted_by_a_committed_batch_of_a_failed_save_evicts_Children_readers_of_its_new_parent`; `RandomWorkloadTests.After_each_random_write_every_cached_read_matches_a_fresh_one`.

## SLUICE-EF-013 A changed owned row invalidates its owner as a modified row

**Rule:** an owned entry that is Added, Modified or Deleted is captured as its first non-owned owner, found among the tracked entries by the ownership key, in state Modified. Nothing is derived from the owned type itself.
**Why:** EF tracks an owned value as its own entry and leaves the owner Unchanged, but readers only see owned values through the owner.
**Accepts:** each changed owned row scans the tracked entries for its owner.
**Owner:** `CapturedSave.Capture` (with `CapturedSave.OwnerOf`).
**Proof:** `WriteDerivationTests.Changing_an_owned_value_evicts_readers_of_its_owner_though_the_tracker_leaves_the_owner_unchanged`.

## SLUICE-EF-014 Pooled contexts and context factories publish every lease's writes, and only those

**Rule:** contexts from `AddDbContextPool((sp, o) => …)`, `AddPooledDbContextFactory` and `AddDbContextFactory` invalidate what each lease commits, and nothing an earlier lease on the same instance left uncommitted, beyond leftovers that only over-invalidate.
**Why:** a pooled instance keeps its options and interceptors across leases, so per-instance state would leak one lease's writes into another's publish, or lose them.
**Accepts:** a save that ends without an event (an unsuppressed conflict, or an interceptor after Sluice throwing in `SavingChanges`; EF raises `SavingChanges` outside its try, so no failure event fires) stays on the context until its next save, which publishes it (SLUICE-EF-008).
**Owner:** `SluiceInterceptor`.
**Proof:** `PoolingTests.Each_lease_evicts_what_it_commits_and_nothing_an_earlier_lease_left_uncommitted`; for a leftover, `AmbientTransactionTests.A_save_left_behind_by_a_conflict_in_a_disposed_TransactionScope_is_evicted_by_the_next_save_without_failing_it`.

## SLUICE-EF-015 Inside a compute, every EF command is a query Sluice analysed, on the compute's own context

**Rule:** while a compute runs, every write a `UseSluice` context executes (`SaveChanges`, `ExecuteSql`, `ExecuteUpdate`, `ExecuteDelete`), told apart by the command's source, throws `InvalidOperationException`, a fused fetch included. Outside a fused fetch, a command also throws when it comes from a context the compute didn't get from `read.Db` (the read helpers check this when they're called, too), when its SQL carries no reads tag (raw SQL, EF's raw command builder), or when its tag says what it reads can't be known (SLUICE-EF-016). The message names the command by its first line and says what to do instead. A read helper called with a read other than the running compute's also throws, since it would record on that other compute. The violation is recorded on the compute (SLUICE-CORE-007). Outside a compute nothing is checked.
**Why:** a read Sluice can't attribute records no dependency, so the value built from it goes stale silently; a context from outside the compute can serve tracked state without running SQL; a write inside a compute publishes mid-compute.
**Accepts:** a captured outside context's reads that run no SQL (`Find` of a tracked entity, `Local`, loaded navigations) and raw ADO.NET on a context's connection aren't seen. A context without `UseSluice` isn't checked, though a compute that reads only through one records nothing and throws (SLUICE-CORE-007). Work under `ExecutionContext.SuppressFlow` isn't checked. The message can show constants inlined in SQL.
**Owner:** `TrackedReads.Read`, called from `TrackedReads.CommandInitialized`; `TrackedReads.Query` for the helpers.
**Proof:** `TrackedReadTests.A_command_Sluice_cannot_track_throws_inside_a_compute_and_runs_outside_one`, `A_query_on_a_context_the_compute_did_not_get_from_read_Db_throws`, `A_compute_that_catches_a_violation_caches_nothing_and_its_caller_still_gets_it`, `A_query_after_a_read_From_that_only_records_is_still_checked`, `A_read_helper_called_with_another_compute_s_read_throws`; for the fused fetch, SLUICE-CORE-013's proofs.

## SLUICE-EF-016 Every query records each entity type it reads

**Rule:** when EF compiles a query on a `UseSluice` context, inside a compute or not, the analysis finds every entity type it reads: its roots, joins, subqueries and set operations; every navigation, matched by name on every entity type the instance can be (casts, interfaces, `EF.Property`, property-bag indexers, string `Include`s); skip navigations, with their join type; and, for each type reached, its query filters unless ignored, and, unless `IgnoreAutoIncludes()` (which EF applies to the whole query), what EF auto-includes: the eager-loaded navigations and skip navigations of the type, its base and derived types, and every type those own; until nothing new is reached. Owned types stand for their owner. It tags the query's first root with the root types it reads (`-- Sluice reads: …`), marking a helper's root as covered unless the query reaches that type again. Inside a compute, each command records each named type's whole-type dependency, and the first command of each query and tag that records any logs them at `Information`, once per process. What can't be known instead tags the query `-- Sluice can't track: …`, with what to do instead: a `FromSql`, `SqlQuery`, table-valued function, temporal or unknown root; a mapped database function not `IsBuiltIn`; a type not mapped to a table; a query filter reading the context's state; an `Include` path or `IgnoreQueryFilters` names that aren't constants; a result that can hold any entity the query reaches, when any entity it reaches (or what that owns) loads lazily or holds its context. The analysis never throws: one that fails tags the query `-- Sluice can't track: …` with the exception.
**Why:** a type the analysis misses is cached with no dependency on it, so a write to it leaves the value stale. A whole-type read on a busy type evicts on every write to it, which only shows as database load, so it's logged. EF runs the interceptor only on compile and caches the result, so the analysis runs on every compile and travels with the compiled query in its SQL. Matching navigations by name on every assignable type can only find too many.
**Accepts:** a plain query is evicted by any write to any type it reads; the helpers narrow that for their own root. Every query's SQL carries the tag. EF drops tags from `ExecuteUpdate` and `ExecuteDelete` (SLUICE-EF-020 reads those another way). A query expression interceptor added after `UseSluice` or in `OnConfiguring` rewrites after the analysis. Functions mapped with `IsBuiltIn = true` are trusted. A result of entities is refused when the query reaches a lazy or context-holding entity at all, even one it only filters by, since Sluice doesn't follow which reached entities the result holds. A lazy entity inside an app type isn't seen, and an `object`-typed value in such a result is refused. EF keeps `Include` paths and `IgnoreQueryFilters` names constant, so their refusals are untested. `UseInternalServiceProvider` contexts can't use Sluice. The analysis is one process-wide singleton interceptor, since EF builds an internal service provider per distinct set of them and throws after twenty.
**Owner:** `TrackedReads.QueryCompilationStarting` and its `Analysis`.
**Proof:** `TrackedReadTests.A_query_is_evicted_by_a_write_to_any_type_it_reads_and_not_by_others` (auto-includes through skip navigations and owned values, and a helper's root read again, among others), `A_plain_query_is_evicted_by_any_write_to_its_type_and_by_AllDependencies_but_not_by_another_type`, `A_query_compiled_outside_a_compute_records_its_reads_inside_one`, `A_query_that_reads_whole_types_logs_them_once_and_one_that_reads_only_through_helpers_does_not`, `Explicit_loading_on_the_compute_s_context_records_the_type_it_loads`, `A_command_Sluice_cannot_track_throws_inside_a_compute_and_runs_outside_one`, `A_read_helper_query_may_read_owned_values_and_shape_its_own_rows`, `A_read_helper_query_may_keep_query_filters_on_its_own_columns_or_ignore_them`, `A_query_the_analysis_fails_on_is_tagged_as_untrackable_instead_of_failing_to_compile`; `RandomWorkloadTests.*` (plain views over navigations, many-to-many, joins, subqueries and `Include`).

## SLUICE-EF-018 EF reads refuse a context without `UseSluice`

**Rule:** `read.Entity` and `read.Children` throw `InvalidOperationException` unless the context's options carry the interceptor `UseSluice` adds, and so does `read.Db` for a context its factory makes without it. All three throw `NotSupportedException` for a provider that isn't relational. `read.Db` disposes the context it made before throwing. `read.Db` without a registered `IDbContextFactory<TContext>` throws saying how to register one.
**Why:** the recording of SLUICE-EF-016 and the checks of SLUICE-EF-002 and 015 live in that interceptor's command hook, so without it, or on a provider that runs no commands, a compute would read with them silently off.
**Accepts:** the non-relational refusal is untested, since the suite's only provider is PostgreSQL.
**Owner:** `TrackedReads.EnsureOn`, called by `TrackedReads.Query` and `SluiceReadsExtensions.Db`.
**Proof:** `ReadGuardTests.Reads_on_a_context_without_UseSluice_throw_naming_it`, `Read_Db_without_a_registered_factory_throws_saying_how_to_register_one`.

## SLUICE-EF-019 `set.AllDependencies()` covers the type and every row a delete of it cascades into

**Rule:** `set.AllDependencies()` is the type's `All`, every foreign key the type, a base or a derived type declares, whole, every foreign key pointing at it that cascades or sets to null, whole, and the same cascade closure a tracked delete publishes (SLUICE-EF-012). It refuses a type SLUICE-EF-003 refuses; a bulk delete derives the same dependencies without that check. `set.Dependency(key)` stays the one row's dependency, with no cascades.
**Why:** it's what an app invalidates after a write Sluice can't see, such as a delete in raw SQL, and the database applies the same `ON DELETE` rules to those rows as to those a save deletes.
**Accepts:** the over-invalidation and the model-unknown cascades of SLUICE-EF-012.
**Owner:** `DbSetDependencyExtensions.AllDependencies` (the mapping check) and `ModelSources.AllDependencies` (`ModelSources.UpdateDependencies` plus the cascades), with `ModelSources.CascadingForeignKeys` and `ModelSources.Cascades`.
**Proof:** `WriteDerivationTests.AllDependencies_of_a_principal_set_evicts_readers_of_the_rows_an_ExecuteDelete_cascades_into` (the delete runs on a context without Sluice), `EntityReadTests.An_entity_read_returns_its_row_and_is_evicted_by_its_key_and_by_AllDependencies_only`, `TrackedReadTests.A_plain_query_is_evicted_by_any_write_to_its_type_and_by_AllDependencies_but_not_by_another_type`, `ChildrenReadTests.A_Children_read_is_evicted_by_AllDependencies_of_its_set_but_not_by_its_principal`.

## SLUICE-EF-020 A bulk write is invalidated by the types it may have written, after it commits

**Rule:** an `ExecuteUpdate` or `ExecuteDelete` on a `UseSluice` context, told apart from other commands by the command's source (EF 10 reports both as `ExecuteUpdate`, so the statement says which), publishes for the root of every entity type whose table its SQL names, as the provider delimits it (an unquoted name only as a whole identifier): an `UPDATE` the type's whole-type dependency and every foreign key a row of it may have; anything else (a delete) the dependencies of `set.AllDependencies()` (SLUICE-EF-019). Neither checks the type's mapping, as a save doesn't (SLUICE-EF-012): a table-mapped type whose sibling reads refuse still publishes. It publishes when it has run, failed or been cancelled, since the server may have committed it either way, by SLUICE-EF-007's timing: inside an EF transaction at its commit or rollback, inside an ambient one at completion, otherwise at once, synchronously for a sync call (SLUICE-EF-010); publishing never throws (SLUICE-EF-009).
**Why:** which rows a bulk write changed is unknown, and EF 10 drops query tags from these statements, so the SQL is the only per-execution record of what one wrote. EF reports a cancelled command through `CommandCanceled`, not `CommandFailed`.
**Accepts:** the scan over-matches, which only over-invalidates. Every table the statement names counts as written, including those it only reads: an `ExecuteDelete` of orders filtered by their customer's name evicts every customer read and the closure of a customer delete. A column, alias or string with a table's quoted name, or an unquoted name standing alone, matches it too. Raw SQL (`ExecuteSql`) and writes on a context without `UseSluice` are still invalidated by hand.
**Owner:** `SluiceInterceptor.NonQueryExecuted`, `CommandFailed`, `CommandCanceled` and their async twins, with `ModelSources.Named` (and `ModelSources.Names`), `ModelSources.UpdateDependencies` and `ModelSources.AllDependencies`.
**Proof:** `BulkWriteTests.ExecuteUpdate_evicts_every_read_of_the_type_it_writes_and_no_other`, `ExecuteDelete_also_evicts_reads_of_what_the_database_cascades_to` (both sync and async), `A_bulk_update_that_moves_rows_to_another_parent_evicts_Children_readers_of_both_parents`, `A_bulk_write_that_fails_or_is_cancelled_after_it_ran_is_still_evicted`, `A_bulk_write_to_a_type_whose_sibling_reads_refuse_is_evicted`, `A_bulk_write_in_an_EF_transaction_is_evicted_once_the_transaction_ends`, `A_bulk_write_in_a_TransactionScope_is_evicted_once_the_scope_completes`, `A_bulk_write_names_an_unquoted_table_only_as_a_whole_identifier`, `Sync_ExecuteUpdate_and_ExecuteDelete_evict_without_going_through_async_code`; `RandomWorkloadTests.*` (its bulk edits, re-parents and deletes, alone or in a transaction, aren't invalidated by hand).

## SLUICE-EF-021 `UseSluice` adds its interceptors once per context

**Rule:** `UseSluice` on options that already carry Sluice's interceptors does nothing.
**Why:** EF composes every configuration registered for a context type (`AddDbContextPool` and `AddDbContextFactory` together, say), so it can run twice for one context; twice would capture each save twice, and the second capture would publish the first before its commit.
**Owner:** `SluiceDbContextOptionsBuilderExtensions.UseSluice`.
**Proof:** `ComputeContextTests.UseSluice_twice_on_one_context_adds_its_interceptors_once`, `PoolingTests.Each_lease_evicts_what_it_commits_and_nothing_an_earlier_lease_left_uncommitted` (the pool registered beside a factory).
