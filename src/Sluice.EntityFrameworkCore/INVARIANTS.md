# Invariants

Rules a reasonable-looking change could break. Each names the one place that enforces it and the tests that fail if it stops. Test names are in `tests/Sluice.EntityFrameworkCore.Tests`. The core's rules (`SLUICE-CORE-`) are in `src/Sluice/INVARIANTS.md`. User-facing docs: `docs/guides/ef-core.md`, `strict-reads.md` and `transactions.md`.

## SLUICE-EF-001 A compute's EF reads run on its own context, which tracks nothing by default and loads only what it asks for

**Rule:** `read.Db<TContext>()` returns one context per compute and type, the scoped `TContext` of a DI scope the compute opens for itself (`CreateAsyncScope`, one per compute, held by it), with `QueryTrackingBehavior.NoTracking`, and disposed with that scope when the compute ends (SLUICE-CORE-015). `read.Entity` and `read.Children` return `AsNoTracking()` queries that call `IgnoreAutoIncludes()`; owned navigations still load, since EF ignores `IgnoreAutoIncludes()` for ownership.
**Why:** a context from outside the compute can hand back tracked instances with unsaved edits, or rows it loaded before a write evicted the value, and the cache would serve them to everyone. A fresh context holds only what the compute itself read.
**Accepts:** cached entities are detached; to edit one, load it again. A query with `AsTracking()` tracks into the compute's context, which nobody else sees. The scope disposes by DI's rules, so a dispose that throws stops the rest of the scope's (SLUICE-CORE-015's keep-going applies to the scope as a whole). A `TContext` registered as a singleton (`AddDbContext(…, contextLifetime: ServiceLifetime.Singleton)`) would be shared by every compute, and one compute's configure would change another's state mid-query; EF registers it scoped by default, and transient works too (the scope disposes it). The scope's services are made on the first caller's flow, so one reading the request reads that caller's (SLUICE-EF-022). A singleton `IDbContextFactory` (`AddDbContextFactory`'s default) makes the context from the root provider, so its scoped dependencies throw under scope validation and are root singletons without it. EF applies a helper's `IgnoreAutoIncludes()` to the whole query, so a plain query joined or combined with a helper's loads no auto-included navigations either (and the analysis, SLUICE-EF-016, reads it the same way).
**Owner:** `ComputeContexts.Get` (through `SluiceReadsExtensions.Db`), and `TrackedReads.Query`, which every helper's query starts from.
**Proof:** `ComputeContextTests.A_compute_gets_one_context_that_does_not_track_and_is_disposed_when_it_ends`, `ReadGuardTests.Read_Db_takes_a_context_registered_with_AddDbContext`, `TenantTests.A_configured_context_s_tenant_filter_gives_each_tenant_its_own_rows_whatever_the_caller_s_tenant` (a constructor taking a scoped service, through `AddDbContext` and a scoped factory), `A_context_with_a_scoped_dependency_from_the_default_singleton_factory_fails_saying_how_to_register_it`, `Without_scope_validation_the_default_singleton_factory_gives_every_compute_one_tenant_service`, `EntityReadTests.Reads_do_not_track_so_an_unsaved_edit_on_the_callers_context_is_not_cached`, `TrackedReadTests.A_read_helper_does_not_load_auto_included_navigations`.

## SLUICE-EF-002 EF reads inside a compute refuse to run inside a transaction

**Rule:** while a compute runs, a read on a `UseSluice` context throws `InvalidOperationException` when it executes inside the context's EF transaction, an enlisted one or an ambient one, read from the context when the command runs, as EF's batch executor reads it (so `Enlist=false` doesn't count). The compute's own context never enlists in the caller's transaction (SLUICE-CORE-014), so this catches a transaction the compute opens itself, and reads in a fused fetch on a context that's in one.
**Why:** a compute inside a transaction caches rows others can't see yet, which may roll back, or an old snapshot, and serves them to everyone.
**Accepts:** generic-path computes aren't checked. A raw `DbTransaction` on the context's connection isn't seen.
**Owner:** `TrackedReads.Read`, through `ContextTransaction.Of`, which the write side (SLUICE-EF-007) uses too.
**Proof:** `TrackedReadTests.A_query_that_opens_a_transaction_on_the_compute_s_context_throws`, `A_compute_that_catches_a_violation_caches_nothing_and_its_caller_still_gets_it` (the fused-fetch case); `ReadGuardTests.A_compute_reads_what_is_committed_while_the_caller_s_EF_transaction_is_open`, `A_compute_reads_what_is_committed_inside_an_enlisted_transaction_or_a_TransactionScope`.

## SLUICE-EF-003 Types not mapped to a table are refused

**Rule:** the read helpers, `set.Dependency(key)` and `set.AllDependencies()` throw `NotSupportedException` for keyless types and types mapped with `ToView`, `ToFunction`, `ToSqlQuery` or to no table; inside a compute, a query that reads one throws `InvalidOperationException` (SLUICE-EF-015). A type is mapped when it (unless it's abstract, like a TPC root with no table) and every concrete type under it is stored in a table, since a query of the type returns those too: a table-mapped TPC root with a view-mapped type under it is refused. The check is on each type a query reads, not its root: a query on a table-mapped type whose TPC root also has a view under it is tracked, and records the root's whole-type dependency.
**Why:** no tracked write publishes for those types, so a cached read of one would only expire.
**Accepts:** such data is cached through a fused fetch with a declared `Source`, invalidated by hand.
**Owner:** `ModelSources.EnsureTable`, and `ModelSources.Unmapped` for the query analysis; `TrackedReads.Dependencies` takes the root's source without the check, which the analysis has already made.
**Proof:** `ReadGuardTests.Helper_reads_and_dependencies_of_types_not_mapped_to_a_table_throw`, `A_type_stored_in_a_table_with_a_derived_type_mapped_to_a_view_is_refused`, `TrackedReadTests.A_command_Sluice_cannot_track_throws_inside_a_compute_and_runs_outside_one`; for the TPC root, `EntityReadTests.A_derived_type_shares_its_root_type_dependencies`, `WriteDerivationTests.Editing_a_derived_row_evicts_readers_of_its_root_type_with_TPH_TPT_or_TPC` and `TrackedReadTests.A_query_on_a_table_mapped_type_whose_TPC_root_has_a_view_is_cached_and_evicted_by_a_write_to_it`.

## SLUICE-EF-004 EF keys are typed by the model

**Rule:** a key passed to `read.Entity` or `set.Dependency` has exactly the CLR type of the single-column primary key, and one passed to `read.Children` that of the FK property, nullability ignored; otherwise `ArgumentException` names the expected type. Composite primary keys throw `NotSupportedException` for single-row reads and dependencies.
**Why:** a key of another type (`1L` for an `int` key, a raw value for a typed id) formats to its own text, so a read and a write of one row could record different dependencies.
**Owner:** `ModelSources.EnsureKeyType` and `ModelSources.KeyProperty`.
**Proof:** `ReadGuardTests.A_key_of_the_wrong_type_throws_naming_the_expected_type`, `A_nullable_foreign_key_takes_a_key_of_its_underlying_type`, `Reading_or_invalidating_one_row_by_composite_key_throws_but_the_whole_set_works`.

## SLUICE-EF-005 EF key text is the folded column value

**Rule:** a model-derived key's text is its provider value, through the property's value converter, then folded: `decimal` scale normalised, strings right-trimmed and upper-cased invariantly, `DateTime` (local to UTC) and `DateTimeOffset` as ticks truncated to microseconds, `byte[]` as hex, other `IFormattable` values invariant.
**Why:** values the database treats as equal (`1m` and `1.00m` in `numeric`, `abc` and `ABC` in `citext`) must give one dependency, or a write keyed one way misses a reader keyed the other.
**Accepts:** folding can merge values the database tells apart, which only over-invalidates. Accent- and culture-sensitive collations aren't folded.
**Owner:** `ModelSources.Build` (with `ModelSources.ToProvider`) and `KeyFolding.Fold`.
**Proof:** `FoldedKeyTests.A_numeric_key_read_as_1_is_evicted_by_the_same_value_written_as_1_00`, `A_citext_key_read_in_one_case_is_evicted_by_the_same_key_in_another`, `A_strongly_typed_key_folds_the_value_its_converter_stores`, `KeyFoldingTests.*`.

## SLUICE-EF-006 Model-derived sources are named from the EF model

**Rule:** an entity type's source is named `IEntityType.GetRootType().Name`, a foreign key's `<root type name>[<FK property names, comma-joined>]`, and a unique column's `<declaring type name>(<property name>)` (the declaring type, since a derived type's unique column is its own), built once per model through the core's public `Source<object>(name, format)` and kept as model annotations. Writes use the same sources.
**Why:** reads and writes of derived types (TPH, TPT, TPC), and every `Children` form, must meet on one source. The names are wire format.
**Owner:** `ModelSources.Entity` (unchecked: reads and writes share it, and the public entry points check the mapping first, SLUICE-EF-003), `ModelSources.ForeignKey` and `ModelSources.Unique`.
**Proof:** `EntityReadTests.A_derived_type_shares_its_root_type_dependencies`, `ChildrenReadTests.Each_Children_form_depends_on_the_foreign_key_value_it_reads`, `WriteDerivationTests.Editing_a_derived_row_evicts_readers_of_its_root_type_with_TPH_TPT_or_TPC`, `EntityReadTests.A_delete_through_the_base_type_evicts_every_reader_of_a_derived_type_s_unique_column`.

## SLUICE-EF-007 A tracked write is invalidated after it commits, before the call that committed it returns

**Rule:** a save's invalidations publish once the transaction it ran in has ended, before the call that ended it returns: `SaveChanges` without a transaction; `Commit` or `Rollback` of an EF transaction, on whichever context calls it (disposed without either, nothing); completion of an enlisted or ambient transaction, whatever the outcome. The transaction is read when the save completes, as EF's batch executor reads it. Every context on one `SluiceCache` shares the interceptor, so a commit publishes other contexts' saves in its transaction.
**Why:** publishing before the commit lets a reader re-cache the old row in between, and nothing evicts it until it expires.
**Accepts:** a promoted or distributed transaction can complete after `TransactionScope.Dispose` returns. A scope without `TransactionScopeAsyncFlowOption.Enabled` can leave an async save seeing no transaction, so it publishes at once. Ambient saves publish one batch each, on the completing thread; an EF transaction publishes one de-duplicated batch. A leftover save (SLUICE-EF-008) publishes early, then again from its live transaction. A `DbTransaction` committed outside EF, a commit on a context without `UseSluice`, and a crash between commit and publish aren't covered.
**Owner:** `SluiceInterceptor`.
**Proof:** `PublishTimingTests.Without_a_transaction_a_save_is_evicted_only_once_its_write_has_run`, `Inside_an_EF_transaction_a_save_is_evicted_only_once_the_transaction_commits`, `A_transaction_disposed_without_commit_evicts_nothing_even_when_its_connection_commits_later`, `A_save_on_a_context_sharing_another_context_s_transaction_is_evicted_when_it_commits`, `A_transaction_the_execution_strategy_retries_is_evicted_when_its_retry_commits`, `A_save_whose_transaction_an_interceptor_commits_before_Sluice_sees_the_save_complete_is_evicted`; `AmbientTransactionTests.Inside_a_TransactionScope_a_save_is_evicted_only_once_the_scope_completes_whatever_its_outcome`, `Inside_an_enlisted_transaction_a_save_is_evicted_only_once_it_completes_whatever_its_outcome`, `Contexts_saving_inside_one_TransactionScope_are_all_evicted_when_it_completes`, `With_Enlist_false_a_save_inside_a_TransactionScope_is_evicted_at_once_and_outlives_the_scope`; `RandomWorkloadTests.Once_concurrent_random_reads_and_writes_settle_every_cached_read_matches_a_fresh_one`.

## SLUICE-EF-008 Every save outcome that might have committed something publishes

**Rule:** a failed, cancelled or conflicting save (`SaveChangesFailed`, `SaveChangesCanceled`, `ThrowingConcurrencyException`) publishes what it captured by SLUICE-EF-007's timing, and a save that goes on past a suppressed conflict publishes again. A rollback, a failed commit and a failed savepoint release publish what the transaction's saves wrote; the later commit or rollback still publishes everything. A capture still held when the context saves again (a leftover: an outer save of a nested save, or one ended without an event) publishes at once, and again from the transaction it began in if that's still live, never from the next save's transaction.
**Why:** earlier batches can commit before a later one fails, and a failed commit's outcome is unknown. EF ends an inner save before its outer one, so an outer save not published by then never would be. Over-invalidating is safe; a dropped invalidation isn't.
**Accepts:** failed saves over-invalidate rows that never committed; a savepoint failure and a leftover publish more than once.
**Owner:** `SluiceInterceptor`.
**Proof:** `PublishTimingTests.A_save_that_fails_after_an_earlier_batch_committed_evicts_that_batch`, `A_concurrency_conflict_after_an_earlier_batch_committed_evicts_that_batch`, `A_save_that_goes_on_past_a_suppressed_concurrency_conflict_evicts_what_it_commits_after_it`, `A_save_cancelled_after_an_earlier_batch_committed_evicts_that_batch` (async only: a sync save takes no token), `A_rolled_back_transaction_still_evicts_what_its_saves_wrote`, `A_commit_that_fails_still_evicts_what_its_saves_wrote`, `A_savepoint_that_fails_to_release_does_not_stop_the_commit_evicting_every_save_in_the_transaction`, `A_save_an_interceptor_makes_from_inside_another_save_evicts_what_both_saves_wrote`, `A_committed_save_is_evicted_though_an_interceptor_then_saves_again_in_a_transaction_it_never_commits`, `Inside_an_EF_transaction_a_save_an_interceptor_saves_again_after_is_evicted_once_more_when_the_transaction_commits`; `AmbientTransactionTests.A_save_left_behind_by_a_conflict_in_a_disposed_TransactionScope_is_evicted_by_the_next_save_without_failing_it`.

## SLUICE-EF-009 Publishing after a commit never throws and can't be cancelled

**Rule:** every publish catches any exception and logs it at `Error`, event id 1, through `ILogger<SluiceInterceptor>` from the services passed to `UseSluice` (which throws without logging); the save, bulk write, commit or completion returns normally. Publishing uses the core's token-less `InvalidateAsync` and `Invalidate`, ignoring EF's token.
**Why:** a throw after the commit makes callers retry a committed write; a request cancelled just after its commit must still invalidate.
**Accepts:** a failed publish leaves stale values until they expire, visible only in the log. An L2 that fails a tag write doesn't fail the publish: FusionCache writes the tag again once the L2 is back (auto-recovery). A slow L2 delays `SaveChanges` until the Redis client times out, since FusionCache puts no timeout on writes; the client's timeout and FusionCache's circuit breakers bound it. Inside a transaction, deriving the dependencies happens at `SavedChanges` (a bulk write's when its command ends), before the commit, where a failure still throws. A leftover's are derived inside its publish, so a failure to derive them is logged, not thrown into the unrelated save that found it.
**Owner:** `SluiceInterceptor.Publish` and `SluiceInterceptor.PublishAsync`.
**Proof:** `PublishTimingTests.A_failure_to_invalidate_after_commit_is_logged_and_the_write_returns_normally` (sync and async saves and bulk updates, a commit and a scope's completion), `Cancelling_the_request_just_after_its_save_committed_still_evicts`, `Cancelling_the_request_just_after_its_transaction_committed_still_evicts`; for an L2 that fails writes, the core tests' `MultiNodeTests.A_distributed_cache_that_fails_writes_does_not_make_InvalidateAsync_throw_and_the_tag_is_written_once_it_recovers`.

## SLUICE-EF-010 Sync EF calls publish synchronously

**Rule:** sync `SaveChanges`, `ExecuteUpdate`, `ExecuteDelete`, `Commit`, `Rollback`, their failure paths, and an enlisted or ambient transaction's `TransactionCompleted` event publish through `SluiceCache.Invalidate`, never by blocking on the async path.
**Why:** sync-over-async can deadlock under a synchronization context and ties up a thread-pool thread per call.
**Owner:** `SluiceInterceptor.Publish`.
**Proof:** `PublishTimingTests.Sync_SaveChanges_Commit_Rollback_and_their_failures_evict_without_going_through_async_code`, `BulkWriteTests.Sync_ExecuteUpdate_and_ExecuteDelete_evict_without_going_through_async_code`, `A_sync_bulk_write_that_fails_or_is_cancelled_after_it_ran_evicts_without_going_through_async_code` (`CommandFailed` and `CommandCanceled`), `AmbientTransactionTests.A_completing_TransactionScope_evicts_without_going_through_async_code`. Their L2 throws on any async call, which FusionCache logs as a warning; the first test shows an async call does log one.

## SLUICE-EF-011 Capturing a save doesn't change what EF saves

**Rule:** a save on a context with `UseSluice` writes exactly what it would without it: an edit EF wouldn't detect (with `AutoDetectChangesEnabled` off) stays unsaved and uninvalidated, and a cascade the app's timings leave to the database or set to `Never` isn't applied.
**Why:** an unconditional `DetectChanges()` saves edits the app chose not to detect, and EF's public `CascadeChanges()` forces every cascade.
**Accepts:** with one timing `OnSaveChanges` and the other `Never`, point readers of rows EF cascades during the save through `ClientCascade` or `ClientSetNull` aren't evicted (`Children` readers are; `Cascade` and `SetNull` are covered by SLUICE-EF-012). The tracker may be scanned up to three times per save.
**Owner:** `CapturedSave.Capture`.
**Proof:** `WriteDerivationTests.With_change_detection_off_an_undetected_edit_is_neither_saved_nor_invalidated`, `With_orphan_deletion_off_Sluice_does_not_make_EF_delete_an_orphan`, `With_cascades_on_save_deleting_a_principal_evicts_readers_of_its_tracked_dependents`.

## SLUICE-EF-012 A save invalidates real keys and its foreign keys before and after, or whole when the one before is unknown

**Rule:** each changed row (join and composite-key rows included) invalidates its key and each foreign key's value before and after the save, skipping nulls; originals are read in `SavingChanges`, keys and current values after the save. An original is only trusted where the database must still hold it when a save that succeeds runs: a property of the primary key; or, for a row EF itself updates or deletes (its entry is `Modified` or `Deleted`, not an owner saved for an owned row's sake), a concurrency token of a row stored in one table (`ModelSources.SingleTable`), whose original EF's `WHERE` matches, or any property when the row has a row version (`ModelSources.HasRowVersion`: it's stored in one table, and has a concurrency token the database changes on every write, `ValueGenerated.OnAddOrUpdate` or `OnUpdate`, such as `rowversion` or PostgreSQL's `xmin`). Any other foreign key of a modified or deleted row invalidates its source's `All`, every `Children` reader of it, and the interceptor logs once per entity type per cache that it does so: for lack of a row version (event 3, Information), or because the row is split across tables (event 4, Information). Only a row's own foreign keys log, and not for an owner saved only for an owned row's sake; an alternate key deleted whole doesn't. An added row's foreign keys stay precise: it had no parent before. A foreign key the tracker can't vouch for invalidates every `Children` reader of it too: marked modified with original equal to current (`Update()` of an unloaded object), or an original that's null in a required key or equal to EF's sentinel for the property (the CLR default, such as 0, unless `HasSentinel` says otherwise). A primary key temporary again after a failed save invalidates its type's `All`, and a foreign key still temporary its source's `All`. A deleted row also invalidates every foreign key that references it, by that key's principal value, or whole when that principal key is an alternate key the row version or a concurrency token doesn't vouch for (another writer may have changed it), and whatever the model lets the database do to rows of other types: for each non-ownership foreign key to the row's type (or a base or derived type) whose `DeleteBehavior` is `Cascade` or `SetNull`, the dependent type's `All` (an owned dependent counts as its owner) and every other foreign key of the dependent, whole; for `Cascade`, then the same for the dependent's own cascading foreign keys, each whole, transitively, visiting each type once. Table-per-type links between a derived type's table and its base's are the same row, not a cascade. A row deleted through a base type also invalidates, whole, every foreign key that references only a derived type, and every foreign key only a derived type has, since it may be one. `Restrict`, `NoAction`, `ClientCascade` and `ClientSetNull` add nothing. The closure is built once per type. A write to a type the helpers refuse still publishes without failing the save.
**Why:** EF overwrites originals when it accepts the save, and an unloaded object has none. An original is what EF loaded, not what the database holds when the save runs: EF's `UPDATE` or `DELETE` matches the row by its key (and its concurrency tokens' originals), so it succeeds even if another writer re-parented the row after it was loaded, and the parent the row really left would keep a stale list until it expired. A row version closes that, since EF then fails the save unless the row is unchanged since it was loaded; a token only the app maintains doesn't, when a bulk write, raw SQL or another service re-parents the row without bumping it; a row split across tables (table-per-type, entity splitting) may change in a table its token isn't in; and a change to a row owned in a table of its own writes only that table, so EF checks nothing of the owner's. Generated keys are temporary until the save runs, and again after a failure; database `CASCADE` and `SET NULL` delete or change rows the tracker never loaded, whose keys only a query before the delete could tell (rejected: an extra round trip per delete, and it races other writers).
**Accepts:** `Update()`, stubs and a real default-valued foreign key (a seeded 0) over-invalidate `Children` readers. A stub of a type with a row version, whose version matches the stored one and whose key holds any other value, looks loaded and invalidates the parent it names, so when that isn't the stored one (a nullable key left null, a value from a constructor), the real old parent is missed; without a row version, a stub's keys are invalidated whole like any updated or deleted row's. A delete over-invalidates by whole type: deleting one customer evicts every cached read of orders (and order lines, and every other type it cascades into). Cascades the model doesn't know about (triggers, a database-first schema that drifted from the model) aren't covered. Changes from an interceptor that runs after Sluice's `SavingChanges` aren't captured. Two entity types splitting one table and sharing a non-key column: saving one changes the column, but only its own root's source is invalidated, so the other's `Entity` and `All` readers keep the old value. Without a row version, every update or delete evicts every `Children` list of the row's foreign keys, under every parent (editing one order evicts every customer's cached order list); the log says so once per type, and mapping a row version (on PostgreSQL, `xmin`) restores exact eviction. A row version or a concurrency-token foreign key doesn't make a table-per-type or entity-split row precise, nor an owner saved only because an owned row changed, wherever that row is stored. A token the model marks database-generated that the database doesn't change on every write (`IsRowVersion()` on SQLite without a trigger, a `[Timestamp]` `byte[]` on PostgreSQL rather than `xmin`, a computed column that doesn't depend on the foreign key) is taken as a row version, and the re-parent race comes back.
**Owner:** `CapturedSave` (`Checked`), with the row version test in `ModelSources.HasRowVersion`, the cascade closure in `ModelSources.Cascades`, and the log in `SluiceInterceptor.Capture`.

## SLUICE-EF-016 Every query records each entity type it reads

**Rule:** when EF compiles a query on a `UseSluice` context, inside a compute or not, the analysis finds every entity type it reads: its roots, joins, subqueries and set operations; every navigation, matched by name on every entity type the instance can be (casts, interfaces, `EF.Property`, property-bag indexers, string `Include`s); skip navigations, with their join type; and, for each type reached, its query filters unless ignored, and, unless `IgnoreAutoIncludes()` (which EF applies to the whole query), what EF auto-includes: the eager-loaded navigations and skip navigations of the type, its base and derived types, and every type those own; until nothing new is reached. Owned types stand for their owner. It tags the query's first root with the root types it reads (`-- Sluice reads: …`), marking a helper's root as covered unless the query reaches that type again. Inside a compute, each command records each named type's whole-type dependency, and the first command of each query and tag that records any logs them at `Information`, once per process. What can't be known instead tags the query `-- Sluice can't track: …`, with what to do instead: a `FromSql`, `SqlQuery`, table-valued function, temporal or unknown root; a mapped database function not `IsBuiltIn`; a type not mapped to a table; a query filter reading the context's state other than where it's stored (SLUICE-EF-022), or any other part of a query filter that doesn't read its rows (its own parameter, a query root, or a lambda parameter of a query operator over those) unless that part is built only from what's fixed once the model is built: constants, readonly static fields and get-only static auto-properties holding plain values (primitives, enums, strings, and structs whose fields are all plain, such as decimal, the dates and times, Guid and nullables of those), plain values a compiler-made closure captured, fields of those, `EF.Functions`, `EF.Constant` and `EF.Parameter` of fixed values, and operators, conversions, conditions and construction of fixed plain values that run only the runtime's own code (EF evaluates every other such part afresh each time the query runs, so anything else is refused, naming what it reads: a method call of any kind, static or instance, a built-in database function or an invoked delegate, given no rows; a static property with a body or a setter, such as the clock; a static field that isn't readonly; a member of an object, captured, made or held in a readonly static field; a struct holding an object); an `Include` path or `IgnoreQueryFilters` names that aren't constants; a result that can hold any entity the query reaches, when any entity it reaches (or what that owns) loads lazily or holds its context. Every refused query filter is named in one reason, by its type and its filter name, and the remedy ignores just those by name (`IgnoreQueryFilters(["Tenant"])`), since `IgnoreQueryFilters()` without names drops every filter in the query, soft delete included; for an anonymous filter, which EF can ignore only that way, it says so and says to name it. A refused filter that reads the context's state also says to read it from a field or auto-property instead, which `read.Db`'s configure can set, and, when the refused part is a context property with a body holding a plain value, that marking it `[SluiceContextState]` (and not virtual) and setting its state with `read.Db<TContext>((db, services) => …)` will do (SLUICE-EF-022). `IgnoreQueryFilters()` and `IgnoreAutoIncludes()` inside a query filter's subquery are passed over, so they never switch off the whole query's filters or auto-includes in the analysis. The analysis never throws: one that fails tags the query `-- Sluice can't track: …` with the exception, as a bug in Sluice to report, and says to run the query in a fused fetch meanwhile.
**Why:** a type the analysis misses is cached with no dependency on it, so a write to it leaves the value stale. A filter on a tenant, a user or the time gives each caller its own rows from the same tables, so one cached value would be served to all of them. A whole-type read on a busy type evicts on every write to it, which only shows as database load, so it's logged. EF runs the interceptor only on compile and caches the result, so the analysis runs on every compile and travels with the compiled query in its SQL. Matching navigations by name on every assignable type can only find too many.
**Accepts:** a plain query is evicted by any write to any type it reads; the helpers narrow that for their own root. Every query's SQL carries the tag. EF drops tags from `ExecuteUpdate` and `ExecuteDelete` (SLUICE-EF-020 reads those another way). A query expression interceptor added after `UseSluice` or in `OnConfiguring` rewrites after the analysis. Functions mapped with `IsBuiltIn = true` are trusted when they read the rows, as is `EF.Functions`; any other method given the rows is left to EF, which translates it or refuses it. A captured variable holding a plain value is taken as fixed once the model is built. The check fails closed, so it refuses some filters whose values never change: a pure static call on constants (`TimeSpan.FromDays(30)`, `Guid.Parse("…")`), a readonly static array or frozen set, a SmartEnum-style readonly static instance, a static property with a body (`DateOnly.MinValue`), and the app's own constructors, operators and conversions. A value fixed per process but different on each node sharing an L2 cache (a readonly static region read from configuration) isn't seen; put it in the cache key. With `UseLazyLoadingProxies` on the whole model, every entity type loads lazily, so every query returning entities is refused and only projections are cached. A computed column (or a default, trigger or check) calling a database function that reads another table, as SQL Server allows, isn't seen. A result of entities is refused when the query reaches a lazy or context-holding entity at all, even one it only filters by, since Sluice doesn't follow which reached entities the result holds. A lazy entity inside an app type isn't seen, and an `object`-typed value in such a result is refused. EF keeps `Include` paths and `IgnoreQueryFilters` names constant, so their refusals are untested. `UseInternalServiceProvider` contexts can't use Sluice. The analysis is one process-wide singleton interceptor, since EF builds an internal service provider per distinct set of them and throws after twenty.
**Owner:** `TrackedReads.QueryCompilationStarting` and its `Analysis`.
**Proof:** `TrackedReadTests.A_query_is_evicted_by_a_write_to_any_type_it_reads_and_not_by_others` (auto-includes through skip navigations, owned values, an auto-included type's own auto-includes and a derived type's owned value, a query filter whose subquery ignores filters and auto-includes, a filter reading only what can't change (a column, an enum, captured plain locals, readonly static string, int and Guid fields, `DateTime.MinValue`, a get-only static auto-property, `EF.Property`, a string method on a column and `EF.Functions`), and a helper's root read again, among others), `A_plain_query_is_evicted_by_any_write_to_its_type_and_by_AllDependencies_but_not_by_another_type`, `A_query_compiled_outside_a_compute_records_its_reads_inside_one`, `A_query_that_reads_whole_types_logs_them_once_and_one_that_reads_only_through_helpers_does_not`, `Explicit_loading_on_the_compute_s_context_records_the_type_it_loads`, `A_command_Sluice_cannot_track_throws_inside_a_compute_and_runs_outside_one` (query filters reading the context, a static property, a static method, the clock, a static field that isn't readonly, a readonly static `AsyncLocal`, a captured object, an object it makes, a captured struct holding an object, a built-in database function given no column, and a configuration object's method and field; ## SLUICE-EF-020 A bulk write is invalidated by the types it may have written, after it commits

**Rule:** an `ExecuteUpdate` or `ExecuteDelete` on a `UseSluice` context, told apart from other commands by the command's source (EF 10 reports both as `ExecuteUpdate`, so the statement says which), publishes for the root of every entity type whose table its SQL names, as the provider delimits it, standing alone (not part of a longer identifier, quoted or not): an `UPDATE` the type's whole-type dependency and every foreign key and unique column (SLUICE-EF-023) a row of it may have; anything else (a delete) the dependencies of `set.AllDependencies()` (SLUICE-EF-019). Neither checks the type's mapping, as a save doesn't (SLUICE-EF-012): a table-mapped type whose sibling reads refuse still publishes. It publishes when it has run and reported a row count other than 0 (Npgsql reports the rows the statement itself changed, and -1 when it can't tell, which publishes), failed or been cancelled, since the server may have committed it either way, by SLUICE-EF-007's timing: inside an EF transaction at its commit or rollback, inside an ambient one at completion, otherwise at once, synchronously for a sync call (SLUICE-EF-010); publishing never throws (SLUICE-EF-009).
**Why:** which rows a bulk write changed is unknown, and EF 10 drops query tags from these statements, so the SQL is the only per-execution record of what one wrote. EF reports a cancelled command through `CommandCanceled`, not `CommandFailed`. One that ran and changed no rows changed nothing, and cascaded nothing, since the database cascades from each row it deletes; publishing it anyway let a background job whose `ExecuteUpdate` matched nothing flush every cached read of the type on each run. Inside a transaction it leaves nothing for the commit.
**Accepts:** the scan over-matches, which only over-invalidates. Every table the statement names counts as written, including those it only reads: an `ExecuteDelete` of orders filtered by their customer's name evicts every customer read and the closure of a customer delete. A column, alias or string with a table's name standing alone matches it too. Raw SQL (`ExecuteSql`) and writes on a context without `UseSluice` are still invalidated by hand. A command interceptor that rewrites the SQL so a table no longer appears as the provider quotes it (sharding by a table-name suffix, say) hides that table from the scan, and one that changes the reported row count to 0 hides the write. A statement-level trigger, which fires on 0 rows, is a cascade the model doesn't know about (SLUICE-EF-012).
**Owner:** `SluiceInterceptor.NonQueryExecuted`, `CommandFailed`, `CommandCanceled` and their async twins, with `ModelSources.Named` (and `ModelSources.NamePattern`), `ModelSources.UpdateDependencies` and `ModelSources.AllDependencies`.
**Proof:** `BulkWriteTests.ExecuteUpdate_evicts_every_read_of_the_type_it_writes_and_no_other`, `ExecuteDelete_also_evicts_reads_of_what_the_database_cascades_to` (both sync and async), `A_bulk_write_that_changed_no_rows_evicts_nothing_and_one_that_changed_a_row_evicts` (update and delete, sync and async), `A_bulk_write_that_changed_no_rows_in_a_transaction_evicts_nothing_at_its_commit`, `A_bulk_update_that_moves_rows_to_another_parent_evicts_Children_readers_of_both_parents`, `A_bulk_write_that_fails_or_is_cancelled_after_it_ran_is_still_evicted`, `A_bulk_write_to_a_type_whose_sibling_reads_refuse_is_evicted`, `A_bulk_write_in_an_EF_transaction_is_evicted_once_the_transaction_ends`, `A_bulk_write_in_a_TransactionScope_is_evicted_once_the_scope_completes`, `A_bulk_write_names_an_unquoted_table_only_as_a_whole_identifier`, `Sync_ExecuteUpdate_and_ExecuteDelete_evict_without_going_through_async_code`; `RandomWorkloadTests.*` (its bulk edits, re-parents and deletes, alone or in a transaction, aren't invalidated by hand).

## SLUICE-EF-022 A query filter on the context's state runs only on a context the compute configured

A configure that runs a query sees an unconfigured context.

## SLUICE-EF-023 A unique-column read is evicted by any write that adds, removes or moves its value

**Rule:** `read.Entity(set, column, value)` takes only a column a single-column unique index (filtered or not) or alternate key covers in the model, other than a single-column primary key, which it reads as `read.Entity(set, key)`; a composite one throws `NotSupportedException`, as does a single-column unique one whose value converter stores null as a value (`ConvertsNulls`), which no save publishes, anything else `ArgumentException`. It records one key of the column's source (`ModelSources.Unique`, one per property, its value folded as a key is, SLUICE-EF-005). A save publishes, for each changed row and each unique column of its type: the value it has after the save, or the whole source when that is temporary; and for an update or delete the value it had, read when the save is captured, under SLUICE-EF-012's rule for a foreign key's: only where EF's statement checks the database still holds it (a row version, or the column as a concurrency token, on a row stored in one table), else the whole source, as when the value before is unknown (a row saved without being loaded). A value its converter stores as null counts as null, for a unique column as for a foreign key: no save publishes it, and `read.Entity` and `read.Children` refuse it with `ArgumentException`. A row deleted through a base type also publishes its derived types' unique columns whole. `ExecuteUpdate`, `ExecuteDelete`, `set.AllDependencies()` and the cascade closure publish every unique column a row of the type may have, whole.
**Why:** the reader depends on the row that holds the value, so a write that gives a row the value, changes that row, or takes the value from it changes what the reader read; a write that doesn't must not evict it, or a lookup by slug is evicted by every draft save of any row.
**Accepts:** the model's unique columns bound what a save publishes (one more tag per unique column per changed row); uniqueness itself isn't needed for correctness, so a filtered index counts. Without a row version, a type's updates and deletes evict every reader by its unique columns, and log it once (events 3 and 4, with `Children`). `set.Dependency(key)` doesn't evict readers by a unique column; `AllDependencies()` does.
