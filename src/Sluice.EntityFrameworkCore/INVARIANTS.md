# Invariants

Rules a reasonable-looking change could break. Each names the one place that enforces it and the tests that fail if it stops. Test names are in `tests/Sluice.EntityFrameworkCore.Tests`. The core's rules (`SLUICE-CORE-`) are in `src/Sluice/INVARIANTS.md`. User-facing docs: `docs/guides/ef-core.md`, `strict-reads.md` and `transactions.md`.

## SLUICE-EF-001 A compute's EF reads run on its own context, which tracks nothing by default and loads only what it asks for

**Rule:** `read.Db<TContext>()` returns one context per compute and type, made in a DI scope the compute opens for itself (`CreateAsyncScope`, one per compute, held by it), with `QueryTrackingBehavior.NoTracking`, and disposed when the compute ends (SLUICE-CORE-015): the contexts it built first, then the probe scopes, then the scope with everything it made, each even when one before it throws: one failure reaches the caller as itself, several as an `AggregateException`; then it lets go of the contexts, built contexts, probe scopes and configure services. The context is the scope's `TContext`, unless its registration is pooled (`DbContextOptions<TContext>` from the scope, or the resolved context's own options, carry `CoreOptionsExtension.MaxPoolSize`): then it's never leased, but built from those options with `ActivatorUtilities`, its other constructor services from the compute's scope, and a lease the scope handed out (a pool the app built by hand) goes back untouched with the scope. The context is made, and EF's `OnConfiguring` run, without the caller's async state (`CleanFlow`, SLUICE-EF-022). Before the configure runs, `read.Db` throws `InvalidOperationException`, recorded as a violation (SLUICE-CORE-007), when the scope's `TContext` is the very instance another scope of the app's root provider gets (a singleton registration, or a factory handing out one instance): a probe scope is opened once per root provider and context type, and its verdict kept; the probe scope is disposed with the compute's; a probe that throws refuses nothing and keeps nothing, and a context known to be shared is refused before it's touched. `read.Entity`, `read.EntityAsync` and `read.Children` return `AsNoTracking()` queries that call `IgnoreAutoIncludes()`; owned navigations still load, since EF ignores `IgnoreAutoIncludes()` for ownership.
**Why:** a context from outside the compute can hand back tracked instances with unsaved edits, or rows it loaded before a write evicted the value, and the cache would serve them to everyone. A fresh context holds only what the compute itself read. A pooled lease goes back to the pool with what the compute's configure set (fields, the connection string), into a request's next lease, and keeps the services an earlier lease's constructor got, and EF has no public way to discard one. A context every scope shares would be shared by every compute and request, and one compute's configure would change it under the others mid-query.
**Accepts:** cached entities are detached; to edit one, load it again. A query with `AsTracking()` tracks into the compute's context, which nobody else sees. The scope disposes by DI's rules, so a dispose that throws stops the rest of the scope's (SLUICE-CORE-015's keep-going applies to the scope as a whole). A pooled context costs one construction per compute that uses it (EF's model and internal services are shared), and a hand-built pool is leased once per compute to see that it's a pool. The probe makes one more context per root provider and type, once; a registration that hands one instance to some scopes and not others isn't seen. A singleton `IDbContextFactory` (`AddDbContextFactory`'s default) makes the context from the root provider, so its scoped dependencies throw under scope validation and are root singletons without it. EF applies a helper's `IgnoreAutoIncludes()` to the whole query, so a plain query joined or combined with a helper's loads no auto-included navigations either (and the analysis, SLUICE-EF-016, reads it the same way).
**Owner:** `ComputeContexts.Get` and `ComputeContexts.Make` (through `SluiceReadsExtensions.Db`; the probe is `ComputeContexts.SharedByScopes`), and `TrackedReads.Query`, which every helper's query starts from.
**Proof:** `ComputeContextTests.A_compute_gets_one_context_that_does_not_track_and_is_disposed_when_it_ends`, `A_context_every_scope_shares_throws_before_its_first_query_and_caches_nothing` (a singleton, and a scoped factory handing out one instance; the configure never runs), `ReadGuardTests.Read_Db_takes_a_context_registered_with_AddDbContext` (scoped and transient), `TenantTests.A_configured_context_s_tenant_filter_gives_each_tenant_its_own_rows_whatever_the_caller_s_tenant` (a constructor taking a scoped service, through `AddDbContext` and a scoped factory), `A_compute_s_context_never_comes_from_the_pool_so_the_next_lease_keeps_nothing_its_configure_set` (EF's pools aren't leased at all, a hand-built one is leased untouched; the next lease keeps neither the tenant nor the connection string), `A_pooled_context_s_marked_property_reads_the_service_the_configure_set`, `The_compute_s_context_is_made_without_the_caller_s_async_state`, `A_context_with_a_scoped_dependency_from_the_default_singleton_factory_fails_saying_how_to_register_it`, `Without_scope_validation_the_default_singleton_factory_gives_every_compute_one_tenant_service`, `ComputeContextTests.When_one_context_s_dispose_throws_the_compute_s_other_contexts_and_scopes_are_still_disposed`, `EntityReadTests.Reads_do_not_track_so_an_unsaved_edit_on_the_callers_context_is_not_cached`, `TrackedReadTests.A_read_helper_does_not_load_auto_included_navigations`.

## SLUICE-EF-002 EF reads inside a compute refuse to run inside a transaction

**Rule:** while a compute runs, a read on a `UseSluice` context throws `InvalidOperationException` when it executes inside the context's EF transaction, an enlisted one or an ambient one, read from the context when the command runs, as EF's batch executor reads it (so `Enlist=false` doesn't count). The compute's own context never enlists in the caller's transaction (SLUICE-CORE-014), so this catches a transaction the compute opens itself, and reads in a fused fetch on a context that's in one. In a fused fetch, a read on a context without `UseSluice` throws the same way when that context is in a transaction (`ContextTransaction.Of`), and a command with no context throws everywhere in a compute, a fused fetch included (SLUICE-EF-015).
**Why:** a compute inside a transaction caches rows others can't see yet, which may roll back, or an old snapshot, and serves them to everyone.
**Accepts:** generic-path computes aren't checked. A raw `DbTransaction` on the context's connection isn't seen.
**Owner:** `TrackedReads.Read`, through `ContextTransaction.Of`, which the write side (SLUICE-EF-007) uses too, and `ForeignContexts.OnNext`; the message is `TrackedReads.InTransaction`.
**Proof:** `TrackedReadTests.A_query_that_opens_a_transaction_on_the_compute_s_context_throws`, `A_compute_that_catches_a_violation_caches_nothing_and_its_caller_still_gets_it` (the fused-fetch case), `A_query_on_a_context_without_UseSluice_runs_in_a_fused_fetch_and_a_save_a_read_in_a_transaction_or_a_command_with_no_context_there_throws`; `ReadGuardTests.A_compute_reads_what_is_committed_while_the_caller_s_EF_transaction_is_open`, `A_compute_reads_what_is_committed_inside_an_enlisted_transaction_or_a_TransactionScope`.

## SLUICE-EF-003 Types not mapped to a table are refused

**Rule:** the read helpers, `set.Dependency(key)` and `set.AllDependencies()` throw `NotSupportedException` for keyless types and types mapped with `ToView`, `ToFunction`, `ToSqlQuery` or to no table; inside a compute, a query that reads one throws `InvalidOperationException` (SLUICE-EF-015). A type is mapped when it (unless it's abstract, like a TPC root with no table) and every concrete type under it is stored in a table, since a query of the type returns those too: a table-mapped TPC root with a view-mapped type under it is refused. The check is on each type a query reads, not its root: a query on a table-mapped type whose TPC root also has a view under it is tracked, and records the root's whole-type dependency.
**Why:** no tracked write publishes for those types, so a cached read of one would only expire.
**Accepts:** such data is cached through a fused fetch with a declared `Source`, invalidated by hand.
**Owner:** `ModelSources.EnsureTable`, and `ModelSources.Unmapped` for the query analysis; `TrackedReads.Dependencies` takes the root's source without the check, which the analysis has already made.
**Proof:** `ReadGuardTests.Helper_reads_and_dependencies_of_types_not_mapped_to_a_table_throw`, `A_type_stored_in_a_table_with_a_derived_type_mapped_to_a_view_is_refused`, `TrackedReadTests.A_command_Sluice_cannot_track_throws_inside_a_compute_and_runs_outside_one`; for the TPC root, `EntityReadTests.A_derived_type_shares_its_root_type_dependencies`, `WriteDerivationTests.Editing_a_derived_row_evicts_readers_of_its_root_type_with_TPH_TPT_or_TPC` and `TrackedReadTests.A_query_on_a_table_mapped_type_whose_TPC_root_has_a_view_is_cached_and_evicted_by_a_write_to_it`.

## SLUICE-EF-004 EF keys are typed by the model

**Rule:** a key passed to `read.Entity` or `set.Dependency` has exactly the CLR type of the single-column primary key, and one passed to `read.Children` that of the FK property, nullability ignored; otherwise `ArgumentException` names the expected type. Composite primary keys throw `NotSupportedException` for single-row reads and dependencies.
**Why:** a key of another type (`1L` for an `int` key, a raw value for a typed id) formats to its own text, so a read and a write of one row could record different dependencies.
**Owner:** `ModelSources.EnsureKeyType` and `ModelSources.KeyProperty`.
**Proof:** `ReadGuardTests.A_key_of_the_wrong_type_throws_naming_the_expected_type`, `A_nullable_foreign_key_takes_a_key_of_its_underlying_type`, `Reading_or_invalidating_one_row_by_composite_key_throws_but_the_whole_set_works`.

## SLUICE-EF-005 EF key text is the folded column value

**Rule:** a model-derived key's text is its provider value, through the property's value converter, then folded: `decimal` scale normalised, strings right-trimmed and upper-cased invariantly, `DateTime` (local to UTC), `DateTimeOffset`, `TimeSpan` and `TimeOnly` as ticks truncated toward zero to microseconds, as every connector sends them, `byte[]` as hex, other `IFormattable` values invariant. Every value converter on a key, foreign key or unique column (`ModelSources.UniqueColumns`) must round-trip (converting any stored value to .NET and back gives that stored value): Sluice refuses the model with `InvalidOperationException`, naming each such property and its converter, unless the converter's class is marked `[SluiceRoundTrips]` (not inherited) or is one of EF's built-ins that give back every value they can load: `EnumToNumberConverter` and `CastingConverter` where the model type holds every value of the provider type (the same type, an integer into a wider or equal integer range, any integer into `decimal`, `float` into `double`), `DateTimeToTicksConverter` and `GuidToBytesConverter`. The check runs once per model, before any of its sources is built (so every read, `set.Dependency` and `set.AllDependencies` refuses it), and when a save's first command or a bulk command is initialised, before anything is written. A converter that stores null as a value on a unique column isn't checked: no read or save uses that column by value (SLUICE-EF-023). The same check then refuses such a column whose `DateTime`, `DateTimeOffset`, `TimeSpan` or `TimeOnly` provider value the database stores less precisely than to the microsecond (for a date, store type `date`, `smalldatetime` or a time-of-day type (`time`, `timetz`, `time with time zone`, `time without time zone`), which drops the date, at any size; SQL Server's `datetime` at any size, since EF writes the model's precision into a store type that takes none; for any of them, a size under 6; and a type without a size unless its provider is known to keep microseconds without one: PostgreSQL's timestamps, `interval` and `time`, SQL Server's `datetime2`, `datetimeoffset` and `time` and SQLite's `TEXT`, so MySQL's unsized types, which keep whole seconds, and any type of a provider Sluice doesn't know need a size of 6 or more; the size is the one the column type carries, read from the store type (`datetime(6)`), and only for a date, time or interval type, so a model precision a provider leaves out of the column doesn't count; the provider told by the mapping's assembly, the name EF's own provider checks compare), naming each property and its store type; `[SluiceRoundTrips]` doesn't lift it.
**Why:** values the database treats as equal (`1m` and `1.00m` in `numeric`, `abc` and `ABC` in `citext`) must give one dependency, or a write keyed one way misses a reader keyed the other. A save reports the value it would write back for what EF loaded, and a reader the value it asked for, so a converter that loads one stored value and writes back another (`"01"` loaded as 1 and written as `"1"`, a GUID stored with braces, `" Active"` parsed as an enum) leaves the readers of what the database held serving stale data. A date column that rounds what a save writes holds a value other than the one a save reports for a new row or a reader asks by, so the two give the row different key text. Only the converter's author knows whether it round-trips, so the app vouches for it once, on the class; Sluice never sees the stored value. Every string-parsing built-in accepts more than one spelling of a value, a narrowing or rounding cast loses values, `DateTimeToBinaryConverter` reads kind bits `ToBinary` never writes, and the bool converters read every value but the true one as false, so none is on the list.
**Accepts:** folding can merge values the database tells apart, which only over-invalidates. Accent- and culture-sensitive collations aren't folded. The mark is the app's promise, and Sluice doesn't check it. A converter composed with `ComposeWith` can't be marked; derive a marked class instead. A typed-id converter from `HasConversion(toProvider, fromProvider)` lambdas has no class to mark, so it moves into one.
**Owner:** `ModelSources.Build` (with `ModelSources.ToProvider`) and `KeyFolding.Fold`; `ModelSources.EnsureRoundTrips` with `ModelSources.EnsurePrecise` (called by `ModelSources.Build`, `CapturedSave.Capture` and `SluiceInterceptor.CommandInitialized`), with `SluiceRoundTripsAttribute`.
**Proof:** `FoldedKeyTests.A_numeric_key_read_as_1_is_evicted_by_the_same_value_written_as_1_00`, `A_citext_key_read_in_one_case_is_evicted_by_the_same_key_in_another`, `A_strongly_typed_key_folds_the_value_its_converter_stores`, `A_model_with_an_unmarked_converter_on_a_key_foreign_key_or_unique_column_is_refused_at_first_use` (a key's lambdas, a foreign key's lambdas, a unique column's enum stored as text, a unique date stored to the millisecond, a unique `DateTime` stored as a `date`; each refused by `AllDependencies`, a save and a bulk delete, before the missing table is touched), `A_unique_date_or_time_is_refused_where_its_provider_stores_it_to_less_than_the_microsecond` (PostgreSQL's and MySQL's own mappings, built without a server: each provider's default, a precision of 6 and MySQL's `datetime(6)` column type trusted, PostgreSQL's unsized `timestamp` trusted, MySQL's unsized `timestamp` and `datetime` refused, and a `DateTimeOffset` in PostgreSQL's `time with time zone`; PostgreSQL's `interval` and `time` and MySQL's `time(6)` trusted for a duration and a time of day, PostgreSQL's `interval(3)` and MySQL's unsized `time` refused), `A_date_store_type_is_imprecise_unless_its_provider_keeps_microseconds` (SQL Server's, SQLite's, Pomelo's and an unknown provider's, by provider name), `A_date_column_s_size_is_the_one_its_type_carries`, `A_time_store_type_is_imprecise_unless_its_provider_keeps_microseconds` (SQL Server's `time`, sized and not, SQLite's and an unknown provider's), `A_marked_converter_and_EF_s_built_ins_that_round_trip_are_trusted` (marked, `EnumToNumberConverter`, `CastingConverter<long, int>`, ticks, Guid bytes), `KeyFoldingTests.*`.

## SLUICE-EF-006 Model-derived sources are named after the tables they read

**Rule:** an entity type's source is named after its root's table, `schema.table` when the model gives a schema (`GetSchema()`), else `table`; a table-per-concrete-type root with no table of its own is named for its concrete types' tables, sorted ordinally and joined with `+`; an owned type is its owner's; a type stored in no table keeps its root's EF name (no read of one is accepted, SLUICE-EF-003). A foreign key's source is `<its type's source name>[<FK column names, comma-joined>]`, and a unique column's `<its declaring type's source name>(<column name>)`, each column named as it is in its type's table. All are built once per model, all of them before the model's first save or bulk write runs a command (`ModelSources.EnsureSources`, after the converter check), through `Sluice.Infrastructure.ModelSource.Create`, which doesn't check model sources against each other, since two models over the same tables share names on purpose, but reserves each name against an app `Source` (SLUICE-CORE-010), and kept as model annotations. Writes use the same sources.
**Why:** reads and writes of derived types (TPH, TPT, TPC), and every `Children` form, must meet on one source; and so must two classes over one table in two contexts (a read model), or table-split types, which a class name can't link. A class rename or move no longer changes any name. The names are wire format.
**Accepts:** classes over one table link only when their key columns, and the schema spelling (`null` versus `"public"`), match: a read model with other key columns, or over one TPT-derived or TPC-concrete table, isn't linked. The same table name in two databases shares a source, which only over-invalidates. A table or schema rename (a migration) changes names; after a rollout that changes names, neither version evicts the other's entries, so the upgrade runs `ClearAsync` once.
**Owner:** `ModelSources.SourceName` and `ModelSources.ColumnName`; `ModelSources.EnsureSources`; `ModelSources.Entity` (unchecked: reads and writes share it, and the public entry points check the mapping first, SLUICE-EF-003), `ModelSources.ForeignKey` and `ModelSources.Unique`.
**Proof:** `EntityReadTests.A_derived_type_shares_its_root_type_dependencies`, `ChildrenReadTests.Each_Children_form_depends_on_the_foreign_key_value_it_reads` (pins `Orders[CustomerId]` and `Notes[CustomerId]`), `WriteDerivationTests.Editing_a_derived_row_evicts_readers_of_its_root_type_with_TPH_TPT_or_TPC`, `Two_classes_mapped_to_one_table_in_two_contexts_evict_each_other` (by key, whole table, foreign key and unique column, both ways), `A_TPC_hierarchy_with_an_abstract_root_is_named_for_its_concrete_types_tables` (pins `Circles+Square` by the tag a key's readers carry), `FoldedKeyTests.A_table_named_like_an_app_source_is_refused_before_a_save_bulk_write_or_read_runs` (`AllDependencies`, a cached `read.Entity`, a save, a bulk write), `EntityReadTests.A_delete_through_the_base_type_evicts_every_reader_of_a_derived_type_s_unique_column`; `UncommittedWriteTests.A_read_of_a_row_the_flow_s_transaction_saved_throws_caches_nothing_and_is_normal_after_commit` (the message shows `Customers:<id>`).

## SLUICE-EF-007 A tracked write is invalidated after it commits, before the call that committed it returns

**Rule:** a save's invalidations publish once the transaction it ran in has ended, before the call that ended it returns: `SaveChanges` without a transaction; `Commit` or `Rollback` of an EF transaction, on whichever context calls it, with or without `UseSluice` (EF's `TransactionCommitted`/`TransactionRolledBack` diagnostics, through `ForeignContexts`; a `TransactionError` publishes and keeps); completion of an enlisted or ambient transaction, whatever the outcome. The transaction is read when the save completes, as EF's batch executor reads it. When the save's context sees no transaction then, but the ambient transaction its first command ran in, or else the one its connection was opened in (`ConnectionOpening`), is still active (a `TransactionScope` without `TransactionScopeAsyncFlowOption.Enabled`, whose async continuation can't see it, and which Npgsql enlists a cold-pool connection in after its first await), the save publishes at once and again when that transaction completes, and logs event 5 (Warning) once per cache; a bulk write records its command's the same way. An EF transaction committed or rolled back outside EF (on the `DbTransaction`, which raises no EF event) has ended when its `DbTransaction` has no connection or refuses to read its isolation level (`ContextTransaction.Ended`): what it holds publishes when Sluice next looks, at the flow's next cached read (SLUICE-EF-025), the context's next `SavingChanges`, a write completing in it, its leftover's handoff, the creation of any command on its context (`CommandCreating`: a provider may refuse the command before any other event, as Npgsql does, and a bulk write has no start), its disposal (EF's `TransactionDisposed` diagnostic, through `ForeignContexts`, since no interceptor sees it: EF disposes its transaction when the app does and when it resets the context, whoever owns the connection; only a transaction EF began: one passed in with `UseTransaction` raises no disposed event, so it publishes at the next of the other points), or its connection starting or joining another transaction (`TransactionStarted`, `TransactionUsed`: a connection runs one transaction at a time), its `DbTransaction` object beginning again (`TransactionStarted`: one just begun has written nothing) or being joined on another connection (`TransactionUsed`), or a context joining it on the same connection (`TransactionUsed`, which publishes what it holds and keeps it, to publish again when it ends), but only once the object is on the context's connection: EF checks that after its started and used events and refuses a transaction from another connection, so neither event publishes anything for one it refuses, opening (`ConnectionOpening`), a pooled context's reset (`PoolReset`: EF closes the connection without an event; only transactions that have ended, by `ContextTransaction.Ended` or no longer `On` the connection, publish), closing (`ConnectionClosing`, and the connection's own `StateChange` to closed or broken, watched from the first write in an EF transaction on it, since the app closes a connection it owns without an EF event), or being disposed (`ConnectionDisposing`), whichever comes first; a transaction a context joined with `UseTransaction`, which EF never disposes and which the app may commit after the context is gone, also publishes at the next cached read on the cache, on any flow (`FlowWrites.BeforeRead`: each such transaction's record is watched from its first write until it publishes, and a read with none watched takes no lock), or at the cache's next sweep, at most a second after it ended (`EfPending.SweepInterval`: a recurring timer on the cache's `TimeProvider`, made with the first watched record and disposed once none are, holding none of the writer's async state, which stops watching once the cache is being disposed); a transaction disposed without commit or rollback publishes at its disposal too, since Sluice can't tell it from one committed outside EF. A write that completes in a transaction that has ended publishes at once with what the transaction held, and neither it nor a leftover is handed to that transaction. A provider may hand the `DbTransaction` object out again on another connection: Npgsql's belongs to the physical connection, which its pool hands to whichever `DbConnection` opens next. So what a transaction holds belongs to the connection it ran on (`EfPending.For`), and a write in the object from another connection publishes that and starts its own. A context still holding an object its provider has handed to another connection (`ContextTransaction.On`: the app closed and opened its connection itself) writes outside it, so the write publishes at once, with what the object holds from the context's own connection, whose transaction has ended (`EfPending.TakeMadeOn`), and the other connection's transaction keeps what it holds. On Npgsql the object moves only once its first `DbConnection` has closed, which publishes first, so these points matter for a provider that raises no `StateChange`. Every context on one `SluiceCache` shares the interceptor, so a commit publishes other contexts' saves in its transaction.
**Why:** publishing before the commit lets a reader re-cache the old row in between, and nothing evicts it until it expires. A save that can't see its scope where it completes would otherwise publish only before the commit. EF raises no event for a raw commit or for disposing a transaction, and a provider may refuse every later command in it (Npgsql does), so Sluice publishes at the first event it does see. A joined transaction the app commits on a connection it keeps open raises none at all, and the next read may be on another server, which would serve the old value until this server's next read, so the sweep bounds that to a second wherever the read is.
**Accepts:** a promoted or distributed transaction can complete after `TransactionScope.Dispose` returns. A save in a scope its context can't see publishes before the commit too, so a read in between caches the old value until the scope completes. A scope left in thread-local storage on a pool thread isn't seen. Ambient saves publish one batch each, on the completing thread; an EF transaction publishes one de-duplicated batch. A leftover save (SLUICE-EF-008) publishes early, then again from its live transaction. A raw commit or rollback publishes late, when Sluice next looks or, for a transaction EF began, when it's disposed, and for a joined one at most a second late; the sweep checks every second while a joined transaction is live, however long the app keeps it; a raw commit followed by a raw `BeginTransaction` on the same connection before Sluice looks publishes the first's writes when a context joins the second, or else when the second ends, since Npgsql hands back the same object and EF raises no event, and until the second ends the flow's cached reads of the first's rows throw as uncommitted (SLUICE-EF-025); since nothing tells that reuse from contexts sharing one live transaction, a join publishes what the object holds early in both cases, which over-invalidates a shared one, and each later join of it publishes everything pending again, with its re-publish (SLUICE-CORE-022); one EF began, never disposed, on a connection the app created and holds open, keeps it pending until then. A transaction disposed without commit over-invalidates what it wrote. A commit, rollback, failure or disposal Sluice sees only through EF's diagnostic events (on a context without `UseSluice`, or a disposal) publishes synchronously, even inside `CommitAsync` or `DisposeAsync`, since a diagnostic observer can't await; so does a connection's `StateChange`, even inside `CloseAsync` or `DisposeAsync`. A crash between commit and publish loses the publish: Sluice keeps no outbox, so the entry's duration bounds it, and an app that needs more calls `InvalidateAsync` from its own outbox's handler.
**Owner:** `SluiceInterceptor` (`Route`, `CommandTransaction`, `RecordOpening`, `CommandCreating`, `TransactionStarted`, `TransactionUsed`, `ConnectionOpening`, `ConnectionClosing`, `ConnectionDisposing`, `TransactionEnded`, `TransactionErred`, `HandToLiveTransaction`, `Earlier`, `PendingIn`, `Closed`, `Joined`, `EfPending.For`, `EfPending.Watch`, `EfPending.TakeEndedWatched`, `Sweep` and `EfPending.StopWatching`, `EfPending.TakeOn`, `EfPending.TakeUnlessOn`, `EfPending.TakeMadeOn`, `Joining`, `Reset`), `PoolReset` and `SluiceOptionsExtension`, `ContextTransaction.On`, `ForeignContexts.OnNext` (the disposal, and a commit, rollback or failure on any context), with `ContextTransaction.Ended` and `ContextTransaction.Active`.
**Proof:** `PublishTimingTests.Without_a_transaction_a_save_is_evicted_only_once_its_write_has_run`, `Inside_an_EF_transaction_a_save_is_evicted_only_once_the_transaction_commits`, `A_transaction_disposed_without_commit_evicts_when_it_is_disposed`, `A_save_on_a_context_sharing_another_context_s_transaction_is_evicted_when_the_transaction_ends_whichever_context_ends_it` (committing context with and without `UseSluice`, commit and rollback, what the transaction holds published at the join and again when it ends; ## SLUICE-EF-008 Every save outcome that might have committed something publishes

**Rule:** a failed, cancelled or conflicting save (`SaveChangesFailed`, `SaveChangesCanceled`, `ThrowingConcurrencyException`) publishes what it captured by SLUICE-EF-007's timing, and a save that goes on past a suppressed conflict publishes again. A rollback, a failed commit and a failed savepoint release or rollback publish what the transaction's saves wrote, undone or not (SLUICE-EF-026); the later commit or rollback still publishes everything. A capture still held when the context saves again (a leftover: an outer save of one an interceptor makes from `SavedChanges`, or one ended without an event) publishes at once, and again from the transaction it ran in if that's still live, told apart by EF's transaction id, never from the next save's transaction, even on the same `DbTransaction` object. A save made from inside another's `SavingChanges` is captured at its own first command and is no leftover.
**Why:** earlier batches can commit before a later one fails, and a failed commit's outcome is unknown. EF ends an inner save before its outer one, so an outer save not published by then never would be. Npgsql hands the same `DbTransaction` out for the next transaction on a connection. Over-invalidating is safe; a dropped invalidation isn't.
**Accepts:** failed saves over-invalidate rows that never committed; a savepoint failure and a leftover publish more than once.
**Owner:** `SluiceInterceptor` (`Save`, `Start`, `HandToLiveTransaction`).
**Proof:** `PublishTimingTests.A_save_that_fails_after_an_earlier_batch_committed_evicts_that_batch`, `A_concurrency_conflict_after_an_earlier_batch_committed_evicts_that_batch`, `A_save_that_goes_on_past_a_suppressed_concurrency_conflict_evicts_what_it_commits_after_it`, `A_save_cancelled_after_an_earlier_batch_committed_evicts_that_batch` (async only: a sync save takes no token), `A_rolled_back_transaction_still_evicts_what_its_saves_wrote`, `A_commit_that_fails_still_evicts_what_its_saves_wrote`, `A_savepoint_that_fails_to_release_does_not_stop_the_commit_evicting_every_save_in_the_transaction`, `A_save_an_interceptor_makes_from_inside_another_save_evicts_what_both_saves_wrote`, `A_committed_save_is_evicted_though_an_interceptor_then_saves_again_in_a_transaction_it_never_commits`, `Inside_an_EF_transaction_a_save_an_interceptor_saves_again_after_is_evicted_once_more_when_the_transaction_commits`; `AmbientTransactionTests.A_save_left_behind_by_a_conflict_in_a_disposed_TransactionScope_is_evicted_by_the_next_save_without_failing_it`; `UncommittedWriteTests.A_save_left_over_from_an_ended_transaction_is_not_pending_in_the_next_one_on_the_connection`; `PublishTimingTests.A_save_left_over_in_a_transaction_committed_outside_EF_is_evicted_when_its_context_saves_again_and_not_kept_for_the_transaction`, `AmbientTransactionTests.Inside_a_TransactionScope_without_async_flow_a_save_left_over_when_its_context_saves_again_is_evicted_again_once_the_scope_completes`.

## SLUICE-EF-009 Publishing after a commit never throws and can't be cancelled

**Rule:** every publish catches any exception and logs it at `Error`, event id 1, through `ILogger<SluiceInterceptor>` from the services passed to `UseSluice` (which throws without logging); the save, bulk write, commit or completion returns normally. Publishing uses the core's token-less `InvalidateAsync` and `Invalidate`, ignoring EF's token.
**Why:** a throw after the commit makes callers retry a committed write; a request cancelled just after its commit must still invalidate.
**Accepts:** a failed publish leaves stale values until they expire, visible only in the log. An L2 that fails a tag write doesn't fail the publish: FusionCache writes the tag again once the L2 is back (auto-recovery). A slow L2 delays `SaveChanges` until the Redis client times out, since FusionCache puts no timeout on writes; the client's timeout and FusionCache's circuit breakers bound it. Inside a transaction, deriving the dependencies happens at `SavedChanges` (a bulk write's when its command ends), before the commit, where a failure still throws. A leftover's are derived inside its publish, so a failure to derive them is logged, not thrown into the unrelated save that found it.
**Owner:** `SluiceInterceptor.Publish` and `SluiceInterceptor.PublishAsync`.
**Proof:** `PublishTimingTests.A_failure_to_invalidate_after_commit_is_logged_and_the_write_returns_normally` (sync and async saves and bulk updates, a commit and a scope's completion), `Cancelling_the_request_just_after_its_save_committed_still_evicts`, `Cancelling_the_request_just_after_its_transaction_committed_still_evicts`; for an L2 that fails writes, the core tests' `MultiNodeTests.A_distributed_cache_that_fails_writes_does_not_make_InvalidateAsync_throw_and_the_tag_is_written_once_it_recovers`.

## SLUICE-EF-011 Capturing a save doesn't change what EF saves

**Rule:** Sluice reads what a save writes when EF initialises the save's first command (`CommandInitialized` with `CommandSource.SaveChanges`, once per save, so later batches and the execution strategy's retries find it captured): after every `SavingChanges` interceptor, EF's own change detection and its cascades and orphan deletions at their configured timings, and before any row is written. It reads the tracker's entries once, with `AutoDetectChangesEnabled` off (restored in a `finally`), so it never detects or cascades anything itself, and a save on a context with `UseSluice` writes exactly what it would without it. An entry EF marked `Modified` with nothing modified (no property, complex property or complex collection, read from `ComplexCollections`, since `EntityEntry.ComplexProperties` leaves collections out), because it shares a row with a changed one (`CommandBatchPreparer.AddUnchangedSharingEntries`: table splitting, an owned type in its owner's table), counts as unchanged. A save with nothing to write runs no command and publishes nothing; one that reports rows written with no command Sluice saw logs event 6 (Error) and publishes every keyed entity type in the context's model whole (`ModelSources.AllDependencies`), since EF has accepted its changes by then and what it wrote can't be read. `UseSluice` adds the reads interceptor before the write interceptor, so a save command the reads interceptor refuses inside a compute (SLUICE-EF-015) is never captured.
**Why:** a capture in `SavingChanges` ran before EF's detection and cascades and before later interceptors, so it missed their changes (an audit row, a soft delete, a dependent EF cascades into); an unconditional `DetectChanges()` saves edits the app chose not to detect, and EF's public `CascadeChanges()` forces every cascade. EF accepts no change until every batch has run, so states and originals are intact at the first command. Event 6 catches a provider or interceptor that writes without a SaveChanges command, which Sluice can't see; over-invalidating is safe, and missing its writes isn't.
**Owner:** `CapturedSave.Capture` (with `CapturedSave.StateOf`); `SluiceInterceptor.CommandInitialized` and `SluiceInterceptor.Save`; `SluiceDbContextOptionsBuilderExtensions.UseSluice` (the order).
**Proof:** `WriteDerivationTests.With_change_detection_off_an_undetected_edit_is_neither_saved_nor_invalidated`, `With_orphan_deletion_off_Sluice_does_not_make_EF_delete_an_orphan`, `With_cascades_on_save_deleting_a_principal_evicts_readers_of_its_tracked_dependents`, `With_cascades_on_save_and_orphan_deletion_off_deleting_a_principal_evicts_readers_of_a_dependent_EF_sets_to_null`, `With_orphan_deletion_on_save_and_cascades_off_an_orphan_EF_deletes_evicts_what_its_delete_cascades_into`, `Changes_an_interceptor_after_Sluice_makes_while_saving_are_invalidated` (sync and async: an edit, an insert and a soft delete), `A_save_with_nothing_to_write_evicts_nothing`, `A_save_refused_inside_a_compute_evicts_nothing`, `Saving_a_column_only_one_split_type_maps_evicts_no_foreign_key_or_unique_column_reader_of_the_other` (the sharing marker), `Changing_only_a_complex_value_evicts_readers_of_its_row`; `PublishTimingTests.A_save_that_reports_rows_written_without_a_command_invalidates_every_type_and_logs_an_error`.

## SLUICE-EF-012 A save invalidates real keys and its foreign keys before and after, or whole when the one before is unknown

**Rule:** each changed row (join and composite-key rows included) invalidates its key and each foreign key's value before and after the save, skipping nulls; originals are read when EF initialises the save's first command (SLUICE-EF-011), keys and current values after the save. An original is only trusted where the database must still hold it when a save that succeeds runs: a property of the primary key; or, for a row EF itself updates or deletes (its entry is `Modified` or `Deleted`, not an owner saved for an owned row's sake), a concurrency token of a row stored in one table (`ModelSources.SingleTable`), whose original EF's `WHERE` matches, or any property when the row has a row version (`ModelSources.HasRowVersion`: it's stored in one table, and has a concurrency token the database changes on every write, `ValueGenerated.OnAddOrUpdate` or `OnUpdate`, such as `rowversion` or PostgreSQL's `xmin`). Any other foreign key of a modified or deleted row invalidates its source's `All`, every `Children` reader of it, and the interceptor logs once per entity type per cache that it does so: for lack of a row version (event 3, Information), or because the row is split across tables (event 4, Information). Only a row's own foreign keys log, and not for an owner saved only for an owned row's sake; an alternate key deleted whole doesn't. An added row's foreign keys stay precise: it had no parent before. A foreign key the tracker can't vouch for invalidates every `Children` reader of it too: marked modified with original equal to current (`Update()` of an unloaded object), or an original that's null in a required key or equal to EF's sentinel for the property (the CLR default, such as 0, unless `HasSentinel` says otherwise). A primary key temporary again after a failed save invalidates its type's `All`, and a foreign key still temporary its source's `All`. A deleted row also invalidates every foreign key that references it, by that key's principal value, or whole when that principal key is an alternate key the row version or a concurrency token doesn't vouch for (another writer may have changed it), and whatever the model lets the database do to rows of other types: for each non-ownership foreign key to the row's type (or a base or derived type) whose `DeleteBehavior` is `Cascade` or `SetNull`, the dependent type's `All` (an owned dependent counts as its owner) and every other foreign key of the dependent, whole; for `Cascade`, then the same for the dependent's own cascading foreign keys, each whole, transitively, visiting each type once. Table-per-type links between a derived type's table and its base's are the same row, not a cascade. A row deleted through a base type also invalidates, whole, every foreign key that references only a derived type, and every foreign key only a derived type has, since it may be one. `Restrict`, `NoAction`, `ClientCascade` and `ClientSetNull` add nothing. A row stored in a table another root entity type maps too (table splitting; `ModelSources.RowSharers`, matched by column, a complex property's columns included, and those of an owned type stored in the row, at any depth) also changes that type's row: a delete publishes its `KeyedDeleteDependencies` by the row's key converted through the stored value (`ModelSources.ValueAs`), or its `AllDependencies` for a composite or unknown key; an insert, or an update that writes a column the other type maps, publishes its row by key, and, whole, each of its foreign keys and unique columns in a column the save writes (an update's modified properties, a complex property's included, read at capture, and what each owned row in it writes: an owned insert or delete every property, an owned update its modified ones, the owner captured as modified when nothing of its own changed); an update of columns only the saved type maps publishes nothing more. A foreign key on the key's columns only (the row's link to itself) isn't one. The closure is built once per type. A write to a type the helpers refuse still publishes without failing the save.
**Why:** EF overwrites originals when it accepts the save, and an unloaded object has none. An original is what EF loaded, not what the database holds when the save runs: EF's `UPDATE` or `DELETE` matches the row by its key (and its concurrency tokens' originals), so it succeeds even if another writer re-parented the row after it was loaded, and the parent the row really left would keep a stale list until it expired. A row version closes that, since EF then fails the save unless the row is unchanged since it was loaded; a token only the app maintains doesn't, when a bulk write, raw SQL or another service re-parents the row without bumping it; a row split across tables (table-per-type, entity splitting) may change in a table its token isn't in; and a change to a row owned in a table of its own writes only that table, so EF checks nothing of the owner's. Generated keys are temporary until the save runs, and again after a failure; database `CASCADE` and `SET NULL` delete or change rows the tracker never loaded, whose keys only a query before the delete could tell (rejected: an extra round trip per delete, and it races other writers).
**Accepts:** `Update()`, stubs and a real default-valued foreign key (a seeded 0) over-invalidate `Children` readers. A stub of a type with a row version, whose version matches the stored one and whose key holds any other value, looks loaded and invalidates the parent it names, so when that isn't the stored one (a nullable key left null, a value from a constructor), the real old parent is missed; without a row version, a stub's keys are invalidated whole like any updated or deleted row's. A delete over-invalidates by whole type: deleting one customer evicts every cached read of orders (and order lines, and every other type it cascades into). Cascades the model doesn't know about (triggers, a database-first schema that drifted from the model) aren't covered. Without a row version, every update or delete evicts every `Children` list of the row's foreign keys, under every parent (editing one order evicts every customer's cached order list); the log says so once per type, and mapping a row version (on PostgreSQL, `xmin`) restores exact eviction. A row version or a concurrency-token foreign key doesn't make a table-per-type or entity-split row precise, nor an owner saved only because an owned row changed, wherever that row is stored. A token the model marks database-generated that the database doesn't change on every write (`IsRowVersion()` on SQLite without a trigger, a `[Timestamp]` `byte[]` on PostgreSQL rather than `xmin`, a computed column that doesn't depend on the foreign key) is taken as a row version, and the re-parent race comes back. Table-split types share one source (SLUICE-EF-006), so any write to the row evicts every type's readers of it, and of the table whole; another type's foreign keys and unique columns in columns the save writes are evicted whole, since that type's values before are unknown.
**Owner:** `CapturedSave` (`Checked`), with the row version test in `ModelSources.HasRowVersion`, the cascade closure in `ModelSources.Cascades`, and the log in `SluiceInterceptor.Capture`; `ModelSources.RowSharers` and `CapturedSave.SharerDependencies` (table splitting).
**Proof:** `WriteDerivationTests.Saving_a_row_another_writer_re_parented_since_it_was_loaded_evicts_Children_readers_of_its_real_parent` (update and delete), ## SLUICE-EF-014 Pooled contexts and context factories publish every lease's writes, and only those

**Rule:** contexts from `AddDbContextPool((sp, o) => …)`, `AddPooledDbContextFactory` and `AddDbContextFactory` invalidate what each lease commits, and nothing an earlier lease on the same instance left uncommitted, beyond leftovers and a transaction disposed without commit (published when it's disposed, SLUICE-EF-007), which only over-invalidate, and are published by the lease that left them, or, for a transaction committed outside EF on a connection the app opened, by the context's reset when it returns to the pool (`PoolReset`, SLUICE-EF-007). **Why:** a pooled instance keeps its options and interceptors across leases, so per-instance state would leak one lease's writes into another's publish, or lose them.
**Accepts:** a save that ends without an event (an unsuppressed conflict) stays on the context until its next save, which publishes it (SLUICE-EF-008).

## SLUICE-EF-015 Inside a compute, every EF command is a query Sluice analysed, on the compute's own context

**Rule:** while a compute runs, every write a `UseSluice` context executes (`SaveChanges`, `ExecuteSql`, `ExecuteUpdate`, `ExecuteDelete`), told apart by the command's source, throws `InvalidOperationException`, a fused fetch included. Outside a fused fetch, a command also throws when it comes from a context the compute didn't get from `read.Db` (the read helpers check this when they're called, too), when its SQL carries no reads tag (raw SQL, EF's raw command builder), or when its tag says what it reads can't be known (SLUICE-EF-016). A command on a context without `UseSluice` (one whose options, `OnConfiguring`'s included, don't carry Sluice's reads interceptor) is seen through EF's diagnostic events instead: one subscription per process to every `DiagnosticListener` named `DbLoggerCategory.Name`, those made before it included, always enabled for `CommandInitialized`; inside a compute, such a command, throws `InvalidOperationException` when it initialises, before it runs (EF opens the connection first): a write anywhere, a read outside a fused fetch, and a read in a fused fetch inside a transaction (SLUICE-EF-002); a command with no context (which may come from either, and names no transaction) throws everywhere in a compute, a fused fetch included: EF runs one only for a provider's own work (Npgsql's HiLo key sequence on Add or Attach), never for a query; the app can run one itself, through EF's raw command builder with no context, and the message names both remedies. The subscription starts when the app registers the package (`AddSluiceEntityFrameworkCore`), before any compute can run, and `UseSluice` throws `InvalidOperationException` when that registration is missing. The message names the command by its first line and says what to do instead. Another running compute's `read`, passed to a helper or asked for `read.Db`, throws by SLUICE-CORE-007, where it records. The violation is recorded on the compute (SLUICE-CORE-007). Outside a compute nothing is checked.
**Why:** a read Sluice can't attribute records no dependency, so the value built from it goes stale silently; a context from outside the compute can serve tracked state without running SQL; a write inside a compute publishes mid-compute. A context without `UseSluice` raises no interceptor Sluice can hook, but EF raises its diagnostic events for every context. EF stops raising a context's command events for a second once a command finds nobody listening, so the listener is always on, not only inside a compute: otherwise a command right after one outside a compute would go unseen.
**Accepts:** a captured outside context's reads that run no SQL (`Find` of a tracked entity, `Local`, loaded navigations) and raw ADO.NET or Dapper on any connection aren't seen (they aren't on EF's diagnostic channel, and Npgsql's `ActivitySource` can't tell EF from raw). Work under `ExecutionContext.SuppressFlow` isn't checked. A context instance that ran a command before the app called `AddSluiceEntityFrameworkCore`, with nothing listening, raises no command events for a second (EF's pause, which nothing outside EF can clear), so its read inside a compute in that second isn't refused; it needs a context to run before the app registers its services. Every command on a context without interceptors costs EF one event object outside a compute too (measured: no difference, about 250 µs a query either way). The message can show constants inlined in SQL.
**Owner:** `TrackedReads.Read`, called from `TrackedReads.CommandInitialized`; `TrackedReads.Query` for the helpers; whether the compute got the context from `read.Db` is `ComputeContexts.StateOf`, by reference; contexts without `UseSluice`, and commands with no context alone, are `ForeignContexts.OnNext` (`Refusal`), subscribed by `ForeignContexts.Subscribe` from `AddSluiceEntityFrameworkCore`.
**Proof:** `TrackedReadTests.A_command_Sluice_cannot_track_throws_inside_a_compute_and_runs_outside_one` (`scalar with no context` included), `A_query_on_a_context_the_compute_did_not_get_from_read_Db_throws`, `A_compute_that_catches_a_violation_caches_nothing_and_its_caller_still_gets_it`, `A_query_after_a_read_From_that_only_records_is_still_checked`, `A_read_helper_called_with_another_compute_s_read_throws` (a helper and `read.Db`), `A_command_on_a_context_without_UseSluice_throws_inside_a_compute_and_runs_outside_one` (`ToListAsync`, `ToList`, `ExecuteSqlRaw`, a read with no context, a write with no context; nothing cached though the compute catches it), `A_command_on_a_context_without_UseSluice_throws_inside_a_compute_even_right_after_it_ran_outside_one`, `A_query_on_a_context_without_UseSluice_runs_in_a_fused_fetch_and_a_save_a_read_in_a_transaction_or_a_command_with_no_context_there_throws`, `ReadGuardTests.Reads_on_a_context_without_UseSluice_throw_naming_it`, `ComputeContextTests.UseSluice_without_AddSluiceEntityFrameworkCore_throws_saying_to_call_it`; in a process of its own, `FreshProcessTests.The_foreign_context_check_starts_at_AddSluiceEntityFrameworkCore_and_covers_listeners_made_before_it` (not refused before the call, refused right after it on a context whose listener EF made before it); for the fused fetch, SLUICE-CORE-013's proofs.

## SLUICE-EF-016 Every query records each entity type it reads

**Rule:** when EF compiles a query on a `UseSluice` context, inside a compute or not, the analysis finds every entity type it reads: its roots, joins, subqueries and set operations; every navigation, matched by name on every entity type the instance can be (casts, interfaces, `EF.Property`, property-bag indexers, string `Include`s); skip navigations, with their join type; and, for each type reached, its query filters unless ignored, and, unless `IgnoreAutoIncludes()` (which EF applies to the whole query), what EF auto-includes: the eager-loaded navigations and skip navigations of the type, its base and derived types, and every type those own; until nothing new is reached. Owned types stand for their owner. It tags the query's first root with the root types it reads (`-- Sluice reads: …`), marking a helper's root as covered unless the query reaches that type again. Inside a compute, each command records each named type's whole-type dependency, and the first command of each query and tag that records any logs them at `Information`, once per process. What can't be known instead tags the query `-- Sluice can't track: …`, with what to do instead: a `FromSql`, `SqlQuery`, table-valued function, temporal or unknown root; a mapped database function not `IsBuiltIn`; a type not mapped to a table; a query filter reading the context's state other than where it's stored (SLUICE-EF-022), or any other part of a query filter that doesn't read its rows (its own parameter, a query root, or a lambda parameter of a query operator over those) unless that part is built only from what's fixed once the model is built: constants, readonly static fields and get-only static auto-properties holding plain values (primitives, enums, strings, and structs whose fields are all plain, such as decimal, the dates and times, Guid and nullables of those), plain values a compiler-made closure captured, fields of those, `EF.Functions`, `EF.Constant` and `EF.Parameter` of fixed values, and operators, conversions, conditions and construction of fixed plain values that run only the runtime's own code (EF evaluates every other such part afresh each time the query runs, so anything else is refused, naming what it reads: a method call of any kind, static or instance, a built-in database function or an invoked delegate, given no rows; a static property with a body or a setter, such as the clock; a static field that isn't readonly; a member of an object, captured, made or held in a readonly static field; a struct holding an object); an `Include` path or `IgnoreQueryFilters` names that aren't constants; a result that can hold any entity the query reaches, when any entity it reaches (or what that owns) loads lazily or holds its context. Every refused query filter is named in one reason, by its type and its filter name, and the remedy ignores just those by name (`IgnoreQueryFilters(["Tenant"])`), since `IgnoreQueryFilters()` without names drops every filter in the query, soft delete included; for an anonymous filter, which EF can ignore only that way, it says so and says to name it. A refused filter that reads the context's state also says to read it from a field or auto-property instead, which `read.Db`'s configure can set, and, when the refused part is a context property with a body holding a plain value, that marking it `[SluiceContextState]` (and not virtual) and setting its state with `read.Db<TContext>((db, services) => …)` will do (SLUICE-EF-022). `IgnoreQueryFilters()` and `IgnoreAutoIncludes()` inside a query filter's subquery are passed over, so they never switch off the whole query's filters or auto-includes in the analysis. The analysis never throws: one that fails tags the query `-- Sluice can't track: …` with the exception, as a bug in Sluice to report, and says to run the query in a fused fetch meanwhile.
**Why:** a type the analysis misses is cached with no dependency on it, so a write to it leaves the value stale. A filter on a tenant, a user or the time gives each caller its own rows from the same tables, so one cached value would be served to all of them. A whole-type read on a busy type evicts on every write to it, which only shows as database load, so it's logged. EF runs the interceptor only on compile and caches the result, so the analysis runs on every compile and travels with the compiled query in its SQL. Matching navigations by name on every assignable type can only find too many.
**Accepts:** a plain query is evicted by any write to any type it reads; the helpers narrow that for their own root. Every query's SQL carries the tag. EF drops tags from `ExecuteUpdate` and `ExecuteDelete` (SLUICE-EF-020 reads those another way). Functions mapped with `IsBuiltIn = true` are trusted when they read the rows, as is `EF.Functions`; any other method given the rows is left to EF, which translates it or refuses it. A captured variable holding a plain value is taken as fixed once the model is built. The check fails closed, so it refuses some filters whose values never change: a pure static call on constants (`TimeSpan.FromDays(30)`, `Guid.Parse("…")`), a readonly static array or frozen set, a SmartEnum-style readonly static instance, a static property with a body (`DateOnly.MinValue`), and the app's own constructors, operators and conversions. A value fixed per process but different on each node sharing an L2 cache (a readonly static region read from configuration) isn't seen; put it in the cache key. With `UseLazyLoadingProxies` on the whole model, every entity type loads lazily, so every query returning entities is refused and only projections are cached. A computed column (or a default, trigger or check) calling a database function that reads another table, as SQL Server allows, isn't seen. A result of entities is refused when the query reaches a lazy or context-holding entity at all, even one it only filters by, since Sluice doesn't follow which reached entities the result holds. A lazy entity inside an app type isn't seen by the result type, but is refused in the value before it's stored (SLUICE-EF-027); an `object`-typed value in such a result is refused here. EF keeps `Include` paths and `IgnoreQueryFilters` names constant, so their refusals are untested. `UseInternalServiceProvider` contexts can't use Sluice. The analysis is one process-wide singleton interceptor, since EF builds an internal service provider per distinct set of them and throws after twenty.
**Owner:** `TrackedReads.QueryCompilationStarting` and its `Analysis`.
**Proof:** `TrackedReadTests.A_query_is_evicted_by_a_write_to_any_type_it_reads_and_not_by_others` (auto-includes through skip navigations, owned values, an auto-included type's own auto-includes and a derived type's owned value, a query filter whose subquery ignores filters and auto-includes, a filter reading only what can't change (a column, an enum, captured plain locals, readonly static string, int and Guid fields, `DateTime.MinValue`, a get-only static auto-property, `EF.Property`, a string method on a column and `EF.Functions`), and a helper's root read again, among others), `A_plain_query_is_evicted_by_any_write_to_its_type_and_by_AllDependencies_but_not_by_another_type`, `A_query_compiled_outside_a_compute_records_its_reads_inside_one`, `A_query_that_reads_whole_types_logs_them_once_and_one_that_reads_only_through_helpers_does_not`, `Explicit_loading_on_the_compute_s_context_records_the_type_it_loads`, `A_command_Sluice_cannot_track_throws_inside_a_compute_and_runs_outside_one` (query filters reading the context, a static property, a static method, the clock, a static field that isn't readonly, a readonly static `AsyncLocal`, a captured object, an object it makes, a captured struct holding an object, a built-in database function given no column, and a configuration object's method and field; the message for a named filter, an anonymous one, two named ones, and named and anonymous ones reached through a navigation, `Include` and an auto-include), `A_read_helper_query_may_read_owned_values_and_shape_its_own_rows`, `A_read_helper_query_may_keep_query_filters_on_its_own_columns_or_ignore_them`, `A_query_that_ignores_just_the_refused_named_filter_keeps_the_others_and_is_evicted_by_a_write`, `A_query_the_analysis_fails_on_is_tagged_as_untrackable_instead_of_throwing`, `A_query_filter_calling_a_static_method_with_a_lambda_that_does_not_read_the_rows_is_tagged_as_untrackable`; ## SLUICE-EF-019 `set.AllDependencies()` covers the type and every row a delete of it cascades into

**Rule:** `set.AllDependencies()` is the type's `All`, every foreign key and unique column (SLUICE-EF-023) the type, a base or a derived type declares, whole, every foreign key pointing at it that cascades or sets to null, whole, the same cascade closure a tracked delete publishes (SLUICE-EF-012), and the same again for every other root type stored in the same rows (table splitting, `ModelSources.RowSharers`), whose rows a delete deletes too. ## SLUICE-EF-020 A bulk write is invalidated by the types it may have written, after it commits

**Rule:** an `ExecuteUpdate` or `ExecuteDelete` on a `UseSluice` context, told apart from other commands by the command's source (EF 10 reports both as `ExecuteUpdate`, so the statement says which), publishes for the root of every entity type whose table its SQL names, as the provider delimits it, standing alone (not part of a longer identifier, quoted or not): an `UPDATE` the type's whole-type dependency and every foreign key and unique column (SLUICE-EF-023) a row of it may have; anything else (a delete) the dependencies of `set.AllDependencies()` (SLUICE-EF-019). A keyed one (`ForKey`, `ForKeys`) narrows its own type's dependencies as SLUICE-EF-024 says, and every other type it names publishes as here. Neither checks the type's mapping, as a save doesn't (SLUICE-EF-012): a table-mapped type whose sibling reads refuse still publishes. It publishes when it has run and reported a row count other than 0 (Npgsql reports the rows the statement itself changed, and -1 when it can't tell, which publishes), failed or been cancelled, since the server may have committed it either way, by SLUICE-EF-007's timing: inside an EF transaction at its commit or rollback, inside an ambient one at completion, otherwise at once, synchronously for a sync call (SLUICE-EF-010); publishing never throws (SLUICE-EF-009). EF initialises a bulk command after refusing a model whose converters Sluice can't trust (SLUICE-EF-005), or one of whose source names the core refuses (SLUICE-EF-006), so no such statement runs; the command also records the ambient transaction it runs in, or its connection was opened in, for SLUICE-EF-007's hidden-scope publish.
**Why:** which rows a bulk write changed is unknown, and EF 10 drops query tags from these statements, so the SQL is the only per-execution record of what one wrote. EF reports a cancelled command through `CommandCanceled`, not `CommandFailed`. One that ran and changed no rows changed nothing, and cascaded nothing, since the database cascades from each row it deletes; publishing it anyway let a background job whose `ExecuteUpdate` matched nothing flush every cached read of the type on each run. Inside a transaction it leaves nothing for the commit.
**Accepts:** the scan over-matches, which only over-invalidates. Every table the statement names counts as written, including those it only reads: an `ExecuteDelete` of orders filtered by their customer's name evicts every customer read and the closure of a customer delete. A column, alias or string with a table's name standing alone matches it too. Raw SQL (`ExecuteSql`) and writes on a context without `UseSluice` are still invalidated by hand. A command interceptor that rewrites the SQL so a table no longer appears as the provider quotes it (sharding by a table-name suffix, say) hides that table from the scan, and one that changes the reported row count to 0 hides the write. A statement-level trigger, which fires on 0 rows, is a cascade the model doesn't know about (SLUICE-EF-012). EF refuses `ExecuteDelete` on a type sharing its table, so a split row is deleted by a tracked delete or raw SQL with `AllDependencies()` (SLUICE-EF-019).
**Owner:** `SluiceInterceptor.NonQueryExecuted`, `CommandFailed`, `CommandCanceled` and their async twins, through `SluiceInterceptor.BulkWrite` and `BulkWritten`, with `ModelSources.Named` (and `ModelSources.NamePattern`), `ModelSources.UpdateDependencies` and `ModelSources.AllDependencies`.
**Proof:** `BulkWriteTests.ExecuteUpdate_evicts_every_read_of_the_type_it_writes_and_no_other`, `ExecuteDelete_also_evicts_reads_of_what_the_database_cascades_to` (both sync and async), `A_bulk_write_that_changed_no_rows_evicts_nothing_and_one_that_changed_a_row_evicts` (update and delete, sync and async), `A_bulk_write_that_changed_no_rows_in_a_transaction_evicts_nothing_at_its_commit`, `A_bulk_update_that_moves_rows_to_another_parent_evicts_Children_readers_of_both_parents`, `A_bulk_write_that_fails_or_is_cancelled_after_it_ran_is_still_evicted`, `A_bulk_write_to_a_type_whose_sibling_reads_refuse_is_evicted`, `A_bulk_write_in_an_EF_transaction_is_evicted_once_the_transaction_ends`, `A_bulk_write_in_a_TransactionScope_is_evicted_once_the_scope_completes`, `A_bulk_write_names_an_unquoted_table_only_as_a_whole_identifier`, `Sync_ExecuteUpdate_and_ExecuteDelete_evict_without_going_through_async_code`, `A_bulk_write_to_a_split_table_evicts_every_type_sharing_it`, `A_bulk_write_in_a_TransactionScope_without_async_flow_is_evicted_again_once_the_scope_completes`; `RandomWorkloadTests.*` (its bulk edits, re-parents and deletes, keyed or not, alone or in a transaction, aren't invalidated by hand).

## SLUICE-EF-021 `UseSluice` adds its interceptors once per context

**Rule:** `UseSluice` on options that already carry Sluice's interceptors does nothing. Otherwise it adds the reads interceptor (`TrackedReads`) before the write interceptor (`SluiceInterceptor`), and `SluiceOptionsExtension`, whose `PoolReset` EF resets with the context, so a command the reads interceptor refuses inside a compute throws before the write interceptor captures it (SLUICE-EF-011).
**Why:** EF composes every configuration registered for a context type (`AddDbContextPool` and `AddDbContextFactory` together, say), so it can run twice for one context; twice would capture each save twice, and the second capture would publish the first before its commit. Captured first, a refused save would publish what it never wrote, from inside the compute.
**Owner:** `SluiceDbContextOptionsBuilderExtensions.UseSluice`.
**Proof:** `ComputeContextTests.UseSluice_twice_on_one_context_adds_its_interceptors_once`, `PoolingTests.Each_lease_evicts_what_it_wrote_and_a_later_lease_s_save_publishes_nothing_an_earlier_lease_wrote` (the pool registered beside a factory), `WriteDerivationTests.A_save_refused_inside_a_compute_evicts_nothing`.

## SLUICE-EF-022 A query filter on the context's state runs only on a context the compute configured

**Rule:** the analysis (SLUICE-EF-016) takes a query filter's read of the context's state as allowed when it reads it where it's stored and the configure can set it: a field that isn't readonly, or a compiler-made auto-property that isn't overridable (an interface's implementation is sealed, so counts) and has a setter that isn't init-only, of the context (the filter's `this`) holding a plain value, or a field or auto-property of such a plain struct held there. It tags such a query `-- Sluice reads the context's state: …`, naming each. Inside a compute, outside a fused fetch, a command with that tag throws `InvalidOperationException`, recorded as a violation (SLUICE-CORE-007), unless its context is one `read.Db<TContext>(configure)` made in this compute and whose configure has returned. `read.Db<TContext>(configure)` runs the configure once, synchronously, on the compute's flow, on the context it has just made, before it returns it to anyone (under a lock a concurrent `read.Db` waits on), and only on the compute's first `read.Db<TContext>`: a configure on a later call throws, and so does one that throws itself, both recorded as violations. A property of the context with a body (not a compiler-made auto-property, which the configure can set already or never), not overridable (an interface's implementation is sealed, so counts), holding a plain value and marked `[SluiceContextState]` counts as such state whatever its visibility; for each such read the analysis compiles a getter, kept in a model runtime annotation by the tag, and on a configured context each command reads it twice, on the compute's flow and without the caller's async state (`CleanFlow.Run`): two values that aren't `Equals`, or a throw without the caller's state, throw `InvalidOperationException`, recorded as a violation, naming the filter and the property but no value. `read.Db<TContext>((db, services) => …)` runs its configure the same way, with the compute's own DI scope, the one the context was made in (pooled contexts included, SLUICE-EF-001), through a provider that resolves every service (`GetService`, `ISupportRequiredService`, `IKeyedServiceProvider`) without the caller's async state. The context itself, its constructor's services and `OnConfiguring` are made without it too. State read any other way (through a method, an unmarked property with a body, or an object the context holds, such as a tenant service) stays untrackable, configured or not; the refusal of an unmarked context property with a body says to mark it and set the state with the `(db, services)` configure.
**Why:** the context's state isn't in the cache key unless the compute puts it there; a context made in the compute's scope otherwise carries what its constructor took. The compute runs on the first caller's flow, so anything made there, or a body read there, that reads the request (`IHttpContextAccessor`, an `AsyncLocal`) reads that caller's, and the value cached for the key is that caller's rows. Made without the caller's state, the context and the configure's services hold only what the configure sets; a body that still reads the caller gives itself away by reading differently without it. A configure on a later call would come after queries ran without it. State behind a method or an object isn't the context's to set.
**Accepts:** Sluice takes on trust, as it takes a fused fetch's dependencies, that the configure sets every piece of state the filters read, from the compute's arguments, and that a marked property's body reads only that state, short of the caller's async state, which is checked: a configure that sets something else leaves what the constructor set, made without a caller, for every caller with that key, and a body reading a static, a `[ThreadStatic]`, a clock coarse enough to read the same twice, or a service it resolves later on the compute's flow that keeps the caller isn't seen. A body reading `Activity.Current`, the culture or an `AsyncLocal` the configure itself set is refused, rightly, since it isn't the context's state. A scoped service whose constructor requires the request (and throws without one) can't be made for a compute. Each command on a configured context with a marked read costs one more read of each, without the caller's state (measured: 64 ns). Dependencies are per entity type and key, not per tenant or database, so a write in one tenant, or one tenant's database, evicts every tenant's reads of that type (or key); `read.Children` on a tenant foreign key narrows that. ## SLUICE-EF-023 A unique-column read is evicted by any write that adds, removes or moves its value

**Rule:** `read.EntityAsync(set, column, value, ct)` takes only a column a single-column unique index (filtered or not) or alternate key covers in the model, other than a single-column primary key, which it reads as `read.Entity(set, key)` does; a composite one throws `NotSupportedException`, as does a single-column unique one whose value converter stores null as a value (`ConvertsNulls`), which no save publishes, anything else `ArgumentException`. ## SLUICE-EF-025 The EF package tells the core what the caller's transactions have written and not committed

**Rule:** what a transaction has pending is exactly what it will publish when it ends (SLUICE-EF-007, 020 and 024), less what a rollback to a savepoint undid (SLUICE-EF-026). A probe copies, because the bypass reads it while a fanned-out task may still be writing. The box keeps a probe per transaction begun, joined or written in on the flow, including one EF begins for a save of its own, until its outermost handle is disposed. Unsaved tracked changes are in no transaction and aren't seen.

## SLUICE-EF-026 Writes rolled back to a savepoint stop counting as pending, and still publish when the transaction ends

**Rule:** for each EF transaction, Sluice keeps a stack of the savepoints EF makes (`CreatedSavepoint(Async)`: EF's own around a save in a transaction, and the app's through EF), each with how much was pending then and the save its context had in progress. `RolledBackToSavepoint(Async)` moves what was written since the innermost savepoint from pending to undone and keeps the savepoint, as PostgreSQL does; if the save in progress when it was made is still the context's, that save's writes are marked undone, so its failure, conflict or leftover handoff adds them as undone too. `ReleasedSavepoint(Async)` pops the innermost. `TransactionFailed` (a failed rollback or release) changes nothing. A savepoint EF makes for a save whose record was taken by a save run inside it (an interceptor saving again from `SavingChanges`) starts the save's record, as its first command does, so a rollback to it still marks that save's writes undone. Undone writes aren't pending (the probe doesn't report them, SLUICE-EF-025), and still publish when the transaction ends, with everything else.
**Why:** a save that fails inside the caller's transaction (EF rolls it back to its own savepoint), a conflict, or an app's unit of work rolled back to a savepoint left those writes pending, so the flow's reads of rows the database had already restored threw, though they'd read what's committed correctly. They still publish at the end because over-invalidating is safe (SLUICE-EF-008), and the rows may have changed and changed back. EF's savepoint events carry no name, so the stack is safe only because Sluice can undo less than the database, never more: it pushes every savepoint EF makes, a rollback pops none and a release pops one, while the database drops at least as many, so Sluice's innermost savepoint is never older than the one the database rolled back to.
**Accepts:** a savepoint made outside EF (ADO.NET's `DbTransaction.Save`) isn't seen, so its writes stay pending (a false throw, which is safe); rolling back through EF to a savepoint made outside EF, after one EF made, would undo more than the database did, so the two mustn't be mixed. SQL Server raises no release event, so its savepoints never pop, which is less precise and still safe.
**Owner:** `SluiceInterceptor.PendingWrites` (`Save`, `RollBack`, `Release`, `Pending`, `All`), `SluiceInterceptor.CreateSavepoint` and `RollBackToSavepoint`, and `SaveInProgress.RolledBack`.
**Proof:** `UncommittedWriteTests.Writes_rolled_back_to_a_savepoint_are_no_longer_pending_and_those_before_it_still_are` (a save and a bulk write, sync and async; the undone write is evicted at the commit), `A_released_savepoint_s_writes_belong_to_the_one_around_it`, `A_savepoint_name_reused_after_a_rollback_shadows_the_first`, `A_save_that_fails_inside_the_flow_s_transaction_leaves_nothing_pending` (sync and async; evicted at the commit), `A_concurrency_conflict_inside_the_flow_s_transaction_leaves_nothing_pending`, `A_rollback_to_a_savepoint_that_fails_leaves_its_writes_pending`, `A_save_that_fails_after_a_save_ran_inside_it_leaves_nothing_of_its_own_pending`.

## SLUICE-EF-027 A cached value holds no lazy loader or context

**Rule:** the EF package registers one store check with its services (`StoreChecks.Add`, SLUICE-CORE-021, from `AddSluiceEntityFrameworkCore`), so it checks the cache's first compute too. Every value about to be stored is walked, whatever context or model it came from, through its fields (never its properties, so none of the app's code runs), with an explicit stack and a set of what it has visited by reference, following arrays' elements and, per runtime type, the fields whose type may hold one: primitives, enums, strings, pointers, reflection objects, execution contexts (a `Task`, a `CancellationToken`'s registrations and a delegate's state capture one; its async-local values reach the compute's own context), and structs or sealed types (and arrays of them) whose fields can't hold one are skipped. A value that reaches an `ILazyLoader` or a `DbContext` is refused with `InvalidOperationException`, which becomes the call's violation (nothing is stored, the caller gets it), naming the query, the type holding it, and the path of fields from the value to it, and saying to select the values into the app's own type instead of the entity.
**Why:** the analysis refuses lazy and context-holding entities by the query's result type (SLUICE-EF-016), but the app's own type can wrap one (`Select(r => new Holder(r))`, or a value built after the query), and a cached one would load related rows later, outside the compute and with no dependency recorded, or keep a context, and what it tracks, alive for every caller. The app can put a context in a value itself, and a lazy entity can come from a context without `UseSluice`, or from before the compute, which no analysis saw. Rejected: a walk that switches on once a lazy model has been seen, which let a `DbContext` through in an app with no lazy model.
**Accepts:** a value holding an execution context (a `Task`, a `CancellationToken` with a registration) isn't walked through it: it keeps the first caller's async-local values alive for the entry's life, and a context reachable only through an async-local of the app's isn't seen: walking an execution context's async-local values would refuse every value that captured a request's flow, since they reach `HttpContext.RequestServices` and the request's `DbContext`. Trimming or AOT that removes fields isn't supported. The walk has no size cap: about 10–18 µs for 10,000 sealed records, about 1.1 ms for 10,000 unsealed ones.
**Owner:** `CachedValues.Check` (the walk), registered by `AddSluiceEntityFrameworkCore`.
**Proof:** `TrackedReadTests.A_lazily_loading_entity_wrapped_in_an_app_type_is_refused_before_it_is_stored` (a constructor-injected loader in a holder, a service-property loader in a DTO, the compute's own context boxed in a list; nothing cached), `A_value_holding_a_lazy_loader_or_a_context_is_refused_whatever_context_it_comes_from` (a lazy entity from a context without `UseSluice` in a fused fetch, the compute's own context from a model with no lazy entities, a context without `UseSluice` that ran no command; the last two build no `UseSluice` options before the compute), `A_value_holding_a_captured_execution_context_is_stored`; the core's `ComputeScopeTests` for the hook.
